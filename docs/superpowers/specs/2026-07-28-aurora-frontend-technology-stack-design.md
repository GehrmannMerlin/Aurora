# Aurora 管理平台前端技术栈设计

## 1. 文档定位

本文是已批准管理平台前端 UX/UI 的后续独立技术选型记录。用户已于 2026-07-28 明确批准整份设计。本文批准只确立前端技术基线，不编写代码、不初始化项目、不创建组件、不进入 `writing-plans`，也不把 `proposed / not-started` ADR 当成实施授权。

已批准 UX/UI 是本专题的需求输入；技术选型不得反向改变 31 个页面的业务边界、权限、URL 语义、状态、数据口径或后端能力缺口。发现冲突时必须先报告并停止受影响选择。

## 2. 权威约束与成功标准

- 管理平台是登录后的高交互应用，没有 SEO、公开内容分发或服务端生成营销页面需求；
- A1—D2 共 31 页需要稳定深链、组织/项目作用域、复杂表格与表单、局部分区加载、`partial` / `stale` / `unavailable`、危险操作和一次性交付秘密；
- 浏览器只能调用正式公开 `platform-api`，不得直连数据库、队列或私有服务，也不得默认增加未设计的 BFF；
- Session 使用 HttpOnly Cookie 和 CSRF 保护；权限、生命周期、允许操作与安全目标均由服务端权威返回；
- 全项目严格 TypeScript；外部输入必须运行时校验；公共契约、错误和敏感数据处理遵守 approved 代码与架构规范；
- 技术栈需要支持分层测试、关键真实浏览器验证、可访问性、响应式布局和后续浏览器矩阵/性能预算；
- 第一版优先降低系统边界和运维复杂度，不能为没有业务需求的 SSR、SEO、BFF 或全局状态增加长期负担。

## 3. 已确认决策

### FE-STACK-001：应用架构与主框架

用户最终选择方案 C：使用严格 TypeScript 的 Vue 3 SPA＋Vite。此前短暂选择的 React 方案已在落盘同步完成前被用户撤回，不作为有效决策。

| 维度 | 已确认结论 |
|---|---|
| 渲染边界 | 纯客户端单页管理应用；不引入 Next.js App Router、React Server Components 或常驻前端服务端渲染运行时 |
| UI 框架 | Vue 3；使用实施锁定时的受支持稳定版本，采用 Single-File Components 与 Composition API，精确版本不得写成浮动 `latest` |
| 开发与构建 | Vite；负责开发服务、代码分割和生产静态资源构建 |
| 服务端边界 | 浏览器只访问正式公开 `platform-api`；不因框架选择增加隐含 BFF |
| 部署含义 | 产物可作为静态资源部署；历史路由回退、同源 Cookie/CSRF 和资源缓存由后续部署专题正式设计 |
| 明确非目标 | SSR、SSG 内容站、SEO 优化、Server Actions、RSC、用前端服务端绕过公开 API |

选择理由：已批准页面主要依赖客户端状态、URL 恢复和高交互工作区；Vue 3 SPA 能以组件、组合式逻辑和响应式状态直接表达这些约束，Vite 保持开发、构建与部署边界简单。当前没有足以抵消额外服务端运行时、缓存、Cookie 转发和安全边界成本的 SSR/SEO 需求。Vue 官方工具链直接支持 Vite、TypeScript 和 SFC 类型检查，适合形成单一工程基线。

该结论是技术设计层确认，不是代码实施授权。框架与构建工具属于长期高迁移成本选择；正式实施前必须按 ADR 规范判断并完成所需 ADR，精确版本和锁文件只在批准的实施计划中确定。

### FE-STACK-002：路由与状态责任组合

用户选择方案 C：使用 Vue Router＋Pinia 中心化状态与自建请求/缓存层，不采用 TanStack Vue Query。

| 责任 | 已确认边界 |
|---|---|
| 路由 | Vue Router 管理嵌套路由、稳定路由名、路径参数和导航生命周期；路由定义必须可生成或声明严格类型 |
| URL Schema | 筛选、搜索、排序、分页、标签和稳定选中对象仍以规范化 URL 为唯一权威；所有路径/查询输入经过运行时 Schema 解析，未知或无效参数不能扩大查询 |
| 服务端状态 | 按业务领域拆分的 Pinia Store 调用统一公开 API 客户端，保存服务端投影及其查询键、版本、水位、完整性、更新时间和陈旧原因；不得维护一个全应用巨型 Store |
| 客户端状态 | 表单草稿、当前页选择、抽屉和对话框优先留在页面/业务 composable；只有真实跨页面共享状态才进入独立 Pinia Store |
| 权限与生命周期 | Session、有效权限、允许操作和资源生命周期仍由服务端 Query 权威决定；路由守卫和 Store 缓存只改善导航体验，不能授权写入或证明资源存在 |
| 持久化 | 不把服务端实体、权限、表单草稿、操作结果或秘密持久化到 `localStorage`；刷新后从 URL、Session 和权威 Query 恢复 |

由于不使用现成服务端状态库，自建层必须在进入实现计划前形成统一且可测试的契约，至少包括：

- 规范化查询键和组织/项目作用域隔离；
- 并发请求去重、取消、过期响应丢弃和作用域切换清理；
- 每类 Query 的新鲜度、失效、后台刷新与分页/游标策略；
- `loading`、`empty`、`error`、`forbidden`、`partial`、`stale`、`unavailable` 的无损映射；
- 只对明确幂等且错误可重试的读取使用有界重试；权限、校验、冲突和限频错误不盲目重试；
- 写操作使用正式幂等/并发上下文；超时先查询 Operation Result 或权威对象，不把重复提交当成缓存重试；
- Command 成功后的精确失效/更新规则，禁止用乐观结果伪造危险操作、权限或生命周期成功；
- API 响应运行时校验、RFC 9457 错误归一化、敏感字段禁止进入通用 Store 日志和 DevTools 快照。

该方案减少第三方服务器状态抽象，但显著增加自建缓存与一致性代码、测试和长期维护责任。此成本是用户选择方案 C 的已知影响，后续不得通过弱化 `partial` / `stale`、并发恢复或公开 API 边界来规避。

### FE-STACK-003：表单、组件、表格与图表基础

用户选择方案 A：PrimeVue＋VeeValidate/Zod＋受控 PrimeVue DataTable＋Apache ECharts。

| 能力 | 已确认边界 |
|---|---|
| UI 组件 | PrimeVue 使用受支持稳定版本和 token 化主题；业务页面通过 Aurora UI 包装层使用高频控件、状态和可访问约束，不在页面中扩散 PrimeVue 私有配置 |
| 表单状态 | VeeValidate Composition API 管理字段值、dirty/touched、提交和字段/页面错误；组件库只负责输入控件与可访问呈现 |
| 运行时 Schema | Zod 作为前端 URL、表单和受信边界前输入的运行时 Schema；正式 API 响应优先消费后端契约生成的类型/校验器，不手工复制另一套业务规则 |
| 权威校验 | 前端 Schema 只做公开契约可表达的格式与组合校验；权限、唯一性、并发、额度和业务状态继续由服务端 Command 权威校验 |
| 表格 | PrimeVue DataTable 使用完全受控的服务端模式；筛选、排序、分页和选择由 Vue Router/Pinia 提供，不启用会改变口径的客户端过滤、排序、分页或总量推断 |
| 图表 | Apache ECharts 仅用于已批准的 C5/C6 选中对象时序；按路由懒加载，必须启用适用 ARIA 能力、颜色外编码和同口径文本摘要，不在前端聚合指标 |

Aurora UI 包装层只统一真实重复的能力：按钮/链接、字段/错误、对话框、状态反馈、标签页、分页、受控表格外壳和图表可访问外壳。它不是另建通用低代码组件系统；不为假想页面抽象组件，也不复制 PrimeVue 的全部 API。

所有危险操作仍使用已批准 UX 的最新权威对象、明确确认和服务端 Command；PrimeVue Confirm/Dialog 只能承载交互，不拥有业务动作、权限或成功状态。一次性交付秘密不得进入表单 Store、通用 UI 状态、表格行缓存、日志或 DevTools 快照。

精确 PrimeVue、VeeValidate、Zod 和 ECharts 版本在实施锁定时共同验证兼容性并固定，不使用浮动 `latest`。组件库和表单 Schema 属于高迁移成本技术基线，正式实施前纳入前端技术栈 ADR 判断。

### FE-STACK-004：质量工具、浏览器验证与性能方法

用户选择方案 A：采用精简分层质量工具链，不在第一版引入 Storybook 或独立视觉测试平台。

| 验证层 | 已确认工具与边界 |
|---|---|
| 静态检查 | `vue-tsc --noEmit` 检查严格 TypeScript 与 Vue 模板类型，ESLint 检查代码规则，Vite production build 验证可构建产物；格式化工具和具体规则从代码规范派生，不再作为产品选择拆问 |
| 单元测试 | Vitest 验证 URL Schema、规范化查询键、自建缓存状态机、错误归一化、数据格式化和纯业务适配逻辑；覆盖率用于发现盲区，不以单一百分比替代风险验证 |
| 组件测试 | Vue Testing Library 在模拟 DOM 中按角色、标签和可见行为测试 Aurora UI 包装组件及页面状态；避免依赖 Vue 实例、PrimeVue 内部 DOM 或大面积快照 |
| API 模拟 | MSW 在 HTTP 边界复现成功、校验失败、权限拒绝、冲突、限频、超时、`partial`、`stale` 与 `unavailable`；处理器只能基于后续正式公开 API 契约建立，当前草案不能冒充契约测试 |
| 真实浏览器 | Playwright 验证关键用户链、URL 前进/后退、焦点、弹窗、表格、危险操作和响应式布局；覆盖 Chromium、Firefox、WebKit 三类引擎；精确支持矩阵和 CI 执行频率以已批准测试/部署/发布设计为设计来源，仍需真实设备与流水线证据 |
| 可访问性 | `@axe-core/playwright` 执行可自动发现的问题检查，并保留人工键盘、焦点顺序、缩放、屏幕阅读器和非颜色信息检查；自动化结果不能宣称完整 WCAG 合规 |
| 视觉回归 | 只为应用壳、核心表单、受控表格、对话框和 C5/C6 图表保留少量 Playwright 截图基线；不把全部 31 页和所有数据组合扩张为第一版视觉快照矩阵 |
| 性能回归 | 检查 Vite 构建清单、入口与路由分包变化，并对代表性认证页面运行 Lighthouse CI；资源/指标阈值和浏览器性能预算已在测试/部署/发布设计中量化，但参考工程与真实部署基线尚不存在 |

常规变更必须能够运行静态检查、相关单元/组件测试和生产构建；关键流程必须有真实浏览器证据。PR、main、nightly、release 的分级门禁与失败治理以已批准测试/部署/发布设计为设计来源；可执行 CI、命令和豁免流程尚不存在。

Vitest、模拟 DOM 和 MSW 提供快速反馈，但不能证明浏览器布局、真实 Cookie/CSRF、服务端权限或正式 API 兼容；Playwright、后续契约测试和真实集成环境分别补足这些边界。第一版不引入 Storybook，未来只有在 Aurora UI 形成跨应用组件产品或独立设计评审需求时才重新评估。

## 4. 完整前端技术方案

### 4.1 运行时与依赖分层

| 层级 | 主要责任 | 禁止越界 |
|---|---|---|
| 应用入口与路由 | Vue 3 应用启动、Vue Router、认证/作用域恢复、页面级懒加载、规范化 URL | 不在路由守卫中把缓存或隐藏菜单当成服务端授权 |
| 页面与业务组合 | 编排已批准的 A1—D2 用户流程、局部状态、表单和页面状态 | 不自行推导新业务状态、权限、统计口径或后端字段 |
| 领域 Store | Pinia 按账号、组织、项目和业务对象保存 Query 投影、元数据及自建缓存状态 | 不建立全应用巨型 Store，不持久化服务端状态、权限、草稿或秘密 |
| 公开 API 客户端 | 统一同源请求、CSRF、取消、错误归一化、运行时响应校验、幂等/并发上下文 | 不访问数据库、队列、私有服务或非公开端点，不把重复 Command 当成网络重试 |
| Schema 与契约适配 | Zod 解析 URL、表单和边界输入；正式 API 存在后优先消费其生成类型/校验器 | 不在前端复制权限、额度、生命周期、唯一性和聚合算法 |
| Aurora UI | 包装 PrimeVue 高频交互、状态、可访问性、主题令牌、受控表格和图表外壳 | 不复制 PrimeVue 全部 API，不形成低代码页面系统，不持有领域 Store |
| 可视化 | Apache ECharts 懒加载并只呈现 C5/C6 服务端时序投影 | 不增加未批准图表，不在浏览器重新聚合、补点或推断健康分数 |

依赖方向保持为“页面 → 业务组合/领域 Store → 公开 API 客户端与契约适配”，页面也可依赖 Aurora UI；Aurora UI 不反向依赖页面或领域 Store。具体包目录、Monorepo 工作区和自动依赖约束必须等待 ADR-001/ADR-006 及工程专题正式授权。

### 4.2 Query 与页面状态流

1. Vue Router 读取路径和查询参数，Zod 将其解析为受限的规范化路由状态；无效参数被拒绝或归一化，不能扩大数据范围。
2. 页面把账号/组织/项目作用域、稳定对象标识和规范化筛选交给对应领域 Store。
3. Store 生成稳定查询键，由统一自建请求层执行去重、取消和过期响应丢弃；切换作用域时隔离或清理不再可见的数据。
4. 正式 API 响应通过运行时边界校验后写入投影，同时保留服务端版本、水位、完整性、更新时间和陈旧原因。
5. 页面按已批准状态模型呈现 `loading`、`empty`、`error`、`forbidden`、`processing`、`partial`、`stale`、`unavailable`；旧数据若保留必须明确标记，不能伪装为新鲜结果。
6. URL 变化是筛选、排序、分页、业务标签和稳定选中对象变化的入口；当前页临时选择、弹窗和未提交表单不写入 URL。

该流程不会定义任何具体端点、字段或 TTL。它们必须由管理平台后端专题的公开 API、错误、分页、数据口径和新鲜度契约提供；在此之前仍是后端能力缺口。

### 4.3 Command 与不确定结果流

1. 页面先读取服务端返回的当前对象版本、有效权限和 `allowedActions`；隐藏或禁用控件只改善体验，不构成授权。
2. VeeValidate 管理交互状态，Zod 执行公开格式/组合校验；服务端再次校验权限、唯一性、额度、生命周期、并发和审计要求。
3. Command 携带正式契约规定的 CSRF、唯一操作编号及版本前置条件；提交期间显示 `processing`，防止当前页面重复触发。
4. 明确成功后，只失效或更新受影响的规范化 Query；危险操作不得依靠乐观更新制造成功。
5. 网络超时或响应丢失时，使用 Operation Result 或权威对象 Query 恢复；如果后端未提供安全恢复能力，页面必须保持不确定并阻止盲目重试。
6. 冲突、权限变化、限频和校验错误进入对应可恢复状态；Session 失效清除受保护内存状态并进入批准的认证恢复流程。

B6 等一次性交付秘密只存在于当前成功页的短暂组件内存；不进入 Pinia、URL、浏览器持久化、通用错误对象、日志、测试截图或 DevTools 可复用快照，离开后立即失去重显能力。

### 4.4 UI、主题和可访问性实现边界

- PrimeVue 提供基础控件，Aurora UI 统一语义状态、字段错误、危险级别、焦点恢复、异步按钮、分页和受控表格契约；业务页面不得直接依赖易变的内部 DOM；
- 使用 PrimeVue token 化主题承载语义颜色、表面、文本、边框、焦点、间距、圆角和密度。精确品牌色与数值不是本技术栈的长期库选择，后续从 `NAV-A` 和 WCAG 约束派生并集中维护，不散落页面；
- 第一版只交付一个统一管理平台主题，不提供用户主题切换或暗色模式入口；没有业务需要时不加载远程字体或装饰性图标集；
- 所有状态必须有文字或图形编码，不能只靠颜色；键盘顺序与视觉顺序一致，动态状态按必要级别宣告，缩放和小屏不隐藏关键状态或危险确认；
- DataTable 的可见总数、排序、筛选和分页全部来自同一服务端查询口径；ECharts 时序同时提供同口径文本摘要、更新时间、水位、采样/降级影响和空值解释。

### 4.5 构建、浏览器与部署边界

- Vite 生成按路由分割的静态 SPA 资源；ECharts 和其他明显重依赖只在相应页面懒加载，不能把全部管理平台打入首个入口块；
- Vite 默认构建目标不是 Aurora 的正式浏览器承诺。`TD-003=A` 浏览器矩阵设计已批准，仍需真实设备证据、可执行 CI 和实施时显式配置；
- 部署必须支持 SPA 历史路由回退，并与正式 Cookie、CSRF、CSP、资源缓存和公开 API 同源/跨域方案一起设计；本专题不选择托管平台；
- 生产 Source Map 的生成、私密上传、保留和外部暴露策略属于部署与安全设计，不能因 Vite 默认配置静默决定；
- 具体包管理器、Node 版本、锁文件、Monorepo 工作区、构建缓存和 CI 平台仍由后续工程及测试/部署/发布专题决定。

## 5. 安全、隐私与失败边界

- Session 仅通过 HttpOnly Cookie 建立，前端不读取或保存长期凭据；所有状态改变请求遵循正式 CSRF 契约，站内继续目标只允许白名单安全路由；
- API、URL、剪贴板内容、上传文件和服务端响应均视为不可信输入；Zod 与正式契约校验失败时进入安全错误状态，不展示原始敏感载荷；
- 权限与资源存在性由服务端决定。`forbidden` 不泄露对象内容，路由守卫、菜单过滤和缓存命中不能取代写操作重新鉴权；
- 通用日志、错误报告、Pinia DevTools、MSW fixture、Playwright trace 和截图不得包含私密令牌、客户端密钥完整值、原始邀请/验证/重置令牌、请求/响应体或 PRD 禁止采集的数据；
- 自建缓存层必须对组织/项目作用域切换、账号退出、权限撤销、资源归档/删除和不确定 Command 结果建立显式清理或失效规则；
- 后端未提供权威状态、数据完整性、操作恢复或获授权目标时，前端显示 `unavailable`/阻塞说明并移除无支撑操作，不通过本地推断填补。

## 7. ADR 判断与实施阻塞

### 7.1 ADR 判断

- Vue 3/Vite、Vue Router/Pinia 自建请求缓存、PrimeVue/VeeValidate/Zod/ECharts 及质量工具共同构成长期、高迁移成本的前端工程基线，需要一份新的前端技术栈 ADR；编号只能在正式 ADR 流程中分配，本文不预占编号、不创建 ADR，也不改变任何 ADR 状态。
- 新 ADR 至少比较本文已记录的候选方案，说明自建缓存层成本、第三方锁定、升级策略、回滚/迁移路线、验证方式和重新评估条件。
- Monorepo 内的具体落位与依赖自动约束还受 ADR-001、ADR-006 影响；二者当前仍为 `proposed / not-started`。ADR-002 界定管理平台与公开协议/后端的边界，同样不能把 proposed 状态误写成实施授权。
- 当前 ADR 索引没有 accepted ADR 与本文冲突，但也没有 accepted ADR 授权创建前端工程。

### 7.2 后端与跨专题阻塞

| 阻塞项 | 当前事实 | 解除条件 |
|---|---|---|
| 正式管理平台 API | 后端设计已批准能力边界，但机器 OpenAPI、请求/响应 Schema 和生成客户端仍不存在 | 按批准后端设计形成并评审可消费契约，不得由前端扩展 |

## 8. 已否决方案

| 方案 | 当前否决原因 |
|---|---|
| Next.js App Router / RSC | 大部分页面仍是高交互客户端工作区；会额外引入前端服务端、RSC 缓存、Cookie 转发和潜在 BFF 边界，而当前没有 SSR/SEO 需求 |
| React SPA＋Vite | 技术上同样可满足 SPA 需求，但用户已撤回此前选择并最终指定 Vue 3；当前第一版不维护两套框架基线 |
| Vue Router＋TanStack Vue Query | 能降低服务端缓存实现成本，但用户选择由 Pinia 和统一自建请求/缓存层承担该职责 |
| Vue Router＋TanStack Vue Query＋Pinia | 状态职责更现成，但用户选择不引入 TanStack Query，并接受自建服务端状态基础设施的额外成本 |
| Element Plus 集成组件方案 | 组件覆盖可满足需求，但用户选择 PrimeVue、独立 VeeValidate/Zod 表单边界和受控 DataTable |
| Reka UI＋Tailwind＋TanStack Table | 可获得更强 DOM/视觉控制，但会在自建请求缓存层之外继续扩大组件、表格和可访问性基础设施；用户选择完整组件套件降低第一版自建量 |
| Storybook 完整组件展示/视觉平台 | 有利于长期组件产品化，但第一版会增加 stories、构建配置和视觉基线维护；当前采用有限 Playwright 截图并保留未来重新评估条件 |
| Playwright 组件测试主导的全浏览器方案 | 真实布局可信度更高，但反馈更慢且需维护组件 story gallery；当前使用 Vitest/Vue Testing Library 快速覆盖，Playwright 聚焦真实浏览器高风险链路 |

否决只针对当前第一版管理平台技术基线；未来若产品边界产生公开内容、强 SSR 或团队能力变化，必须以新需求和 ADR 重新评估，不能在实现中静默切换。
