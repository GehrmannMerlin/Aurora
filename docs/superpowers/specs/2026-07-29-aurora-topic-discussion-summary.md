# Aurora 六专题讨论总结与正式化输入

## 1. 文档目的与使用边界

本文汇总此前六个专题的实际讨论结论，供后续依照 [ADR 规范](<../../../Aurora ADR 规范.md>) 和[文档规范](<../../../Aurora 文档规范.md>)整理为长期有效的 ADR、架构/API/协议/SDK/测试/发布/运维文档。它解决四个问题：

1. 已经明确了什么，批准效力到哪一层；
2. 哪些只是 approved PRD/架构规则或会话设计基线，不能冒充实施规格；
3. 哪些高迁移成本选择需要 ADR，哪些内容应进入普通正式文档；
4. 在进入 `writing-plans` 前还缺哪些公共契约、数据模型、运行参数、评审和证据。

本文不是第二份 PRD，不复制全部页面规格，不分配新 ADR 编号，不修改 ADR-001—006 状态，不创建接口、字段、表、队列、云资源或代码。若本文与 approved PRD、长期规范或未来 accepted ADR 冲突，以更高权威来源为准，并必须回到受影响专题修正。

当前 `status: approved` 表示用户已于 2026-07-29 确认本文可作为 ADR、正式文档树、机器契约、缺口管理和实施就绪审查的正式化输入。它仍不表示候选 ADR 已 `accepted`、缺口已解除或实现已经存在。

确认记录（2026-07-29）：本文继续保持“不是第二份 PRD、不修改 ADR 状态、不代表实现存在”的边界。此次确认不创建或证明 OpenAPI、Schema、数据模型、表、队列、云资源、代码、CI 或测试结果；所有 required ADR、机器契约和验证仍须独立完成。

## 3. 专题一：Monorepo 与工程工具

### 3.1 讨论目标

该专题处理 Aurora 的代码、文档、示例、协议和工程工具如何放在一个仓库中协作，以及如何让模块边界不仅存在于文字中，还能被构建和 CI 自动验证。它直接影响协议原子变更、包版本、依赖方向、受影响测试、制品发布和新会话恢复。

### 3.2 已批准的设计基线

1. 使用统一 Monorepo 管理 SDK、数据接入、数据处理与存储、管理平台、公共协议、示例、文档和工具；
2. 一级目录职责固定为：
   - `apps/`：可部署应用；
   - `packages/`：可复用包和公共协议；
   - `examples/`：可执行接入示例；
   - `docs/`：跨模块长期文档；
   - `tooling/`：共享工程工具；
3. 六份长期规范保留在仓库根目录，是目录规则的明确历史兼容例外；
4. 五大系统逻辑边界不能因为物理同仓或第一版合并部署而消失；
5. 跨包只能通过公开出口，禁止引用其他包的 `src`、`internal` 或未导出路径；
6. 依赖保持单向，公共协议位于底层；Core 不依赖 Browser；插件/框架适配只依赖公开 SDK/协议接口；管理平台不依赖服务端数据库模型；
7. `shared` 不能成为绕过边界的杂物包；临时例外必须有原因、Owner、清理任务和结束条件；
8. CI 最终必须阻止循环、反向、未声明和私有路径依赖，并验证应用/包可独立构建、测试和发布。

这些结论有 approved 架构规则和用户批准基线支撑；ADR-001/ADR-006 仍未 accepted，因此不能据此初始化工作区。

### 3.3 讨论形成的工程原则

- 协议、生产者、消费者、测试样本和文档应能在一个 PR 中原子修改；
- 受影响构建是成本优化，不是正确性边界。根配置、公共协议、依赖矩阵和锁文件变化必须扩大验证范围；
- 包公开出口、模块 README、依赖声明、契约样本和测试随模块同时建立；
- 应用可以独立部署，SDK 包可以独立发布，但不能通过复制协议或类型形成第二权威；
- 测试/部署/发布专题已增加不可变制品、发布清单、SBOM/来源证明和跨包兼容组合要求。

### 3.4 尚未确认或尚无正式规格

- 包管理器与锁文件策略；
- Workspace/任务编排工具、依赖图工具和 Lint/边界检查实现；
- 统一版本还是独立版本、Changelog、Changeset 和 SemVer 发布编排；
- 本地/CI 构建缓存、远程缓存、受影响任务算法和缓存可信边界；
- Node 版本策略、工具链精确版本和升级周期；
- SDK npm 包、应用镜像、SPA 和协议包之间的正式发布关系；
- 目录/包名、公共 exports、测试工具包和配置包的最终清单。

## 4. 专题二：SDK Core、Browser、插件和框架适配

### 4.1 讨论目标与分层

该专题以“SDK 最高优先级是不影响宿主”为中心，把通用生命周期与事件管道、浏览器环境能力、具体采集能力和框架语义分开：

```text
event-schema
      ↑
Core：配置、生命周期、统一事件管道、采样、队列、批量、传输协调
      ↑
Browser：浏览器环境、原生 API 代理、页面生命周期
      ↑
Plugins：错误 / 请求 / 性能 / 基础行为捕获
      ↑
Framework adapters：React / Vue 等框架语义接入
```

箭头表示上层可依赖下层公开接口，不允许反向或循环依赖。

### 4.2 已批准的 Core 边界

- Core 环境无关，不直接访问 `window`、`document`、DOM 或浏览器原生 API；
- Core 管理配置、初始化、重复初始化、启动、停止、`flush`、`destroy`、插件注册、事件管道、采样、批量、内存队列、有界重试和传输协调；
- 所有事件先进入统一运行时校验、隐私/脱敏、采样、队列和上报管道，插件不能绕过；
- 第一版只承诺内存有界队列和批量发送，不承诺浏览器持久离线队列；
- 事件使用稳定编号支持服务端幂等；永久拒绝不重试，暂时失败才按有上限退避重试；
- 多实例不共享不可控可变状态；SDK 自身异常不向宿主抛出，不导致宿主页面不可用。

### 4.3 Browser、插件和框架适配边界

- Browser 通过明确环境接口向 Core 提供时间、调度、网络、页面生命周期和原生 API 包装；
- 对原生 API 的代理集中安装、引用计数/实例隔离并可完整恢复；重复初始化不重复监听；
- 插件只负责监听、捕获、标准化转换和释放，不拥有发送器、独立队列、重试、协议或 Core 私有状态；
- 插件不能依赖其他插件内部实现，也不能形成自己的上报通道；插件失败必须被隔离；
- React/Vue 等适配只补框架错误边界、生命周期或组件语义，不复制 Core/Browser 通用采集；
- `stop`/`destroy` 后监听器、代理、定时器和引用必须清零或恢复，卸载不得污染宿主；
- 默认采集范围保持 PRD 最小化：不采集请求/响应体、凭据、表单、完整 DOM/文本、完整行为轨迹、完整 IP 或指纹。

### 4.4 协议、可靠性与发布约束

- `event-schema` 是事件类型、枚举、限制、运行时 Schema、版本和契约样本的唯一来源；
- TypeScript 类型不能代替外部输入运行时校验；协议包不得包含采集、网络、数据库或页面业务；
- SDK 确认发送只表示服务端完成可靠接收，不表示 Source Map、聚合或问题已经生成；
- SDK 发布必须验证公共 exports、类型、tree-shaking、副作用声明、安装示例、包内容和 SemVer；
- 已批准测试/部署设计提出第一版体积预算：Core ≤10 KiB gzip，Browser＋Core ≤30 KiB gzip，单插件增量 ≤8 KiB，框架适配增量 ≤5 KiB；这些数值已经成为设计目标，仍需基准验证。

### 4.5 关键测试证据

- 无 DOM 的 Core 单元/属性测试；
- 重复初始化、插件异常、多实例、断网、慢网、页面卸载、资源上限和销毁恢复；
- 真实浏览器的监听/代理、字段限制、隐私、递归采集和原生 API 恢复；
- React/Vue 支持版本的安装、框架错误接入和卸载；
- 宿主页面 Long Task、内存、同步包装开销和包体积基准；
- 公共协议合法/非法/边界/旧版本样本在 SDK、接入和处理端复用。

### 4.6 尚未确认或尚无正式规格

- Core 公共 API、配置对象、错误/诊断 API、插件接口、Browser Environment 接口和生命周期签名；
- 插件默认启用集合、错误/请求/性能/行为字段的精确 Schema 与限制；
- Schema 库、SDK 端是否携带完整/轻量校验器、协议版本和支持期限；
- 队列数量、批次大小、flush 时机、重试次数/退避和传输错误码；
- React/Vue 精确公共接入 API、框架版本矩阵和自动安装策略；
- 包拆分、包名、构建产物、兼容/迁移和 npm 版本策略；
- 可复现性能参考页面/设备，预算尚未被实现测量。

## 5. 专题三：数据接入与可靠缓冲

### 5.1 讨论目标与端到端语义

接入层的职责是把不可信 SDK 请求变成“已经完成必要校验并可靠保存、可以后续异步处理”的事件事实。它不执行 Source Map、问题分组、指标聚合或告警。

```text
SDK 批次
→ 身份/密钥/来源/环境
→ 大小/协议/Schema/隐私
→ 去重/采样/限流/资源策略
→ 可靠缓冲写入
→ 返回请求级＋逐事件结果
→ 异步消费者
```

只有可靠缓冲成功后才可返回“已接收”。这个结果明确不等于“问题已生成”或“已经可查询”。

### 5.2 已批准的同步接入边界

- 验证客户端上报密钥、项目、允许来源、允许运行环境、项目生命周期和策略状态；
- 拒绝来源只作为安全证据，不自动加入 allowlist，也不自动创建环境；
- 限制请求/事件大小、批次数量、字符串/数组/对象深度、时间戳、协议版本和禁止字段；
- 所有外部输入通过 `event-schema` 运行时校验；未知类型或不支持版本明确拒绝；
- 执行隐私过滤、必要采样、稳定事件编号去重、组织/项目公平限流和资源保护；
- 一个批次允许部分事件成功、部分事件永久拒绝或暂时失败；单条失败不回滚已经可靠写入的合法事件；
- SDK 对永久拒绝不重试，对明确暂时失败使用有上限退避，避免放大流量；
- 接入路径保持短、可限时、可观测，不同步执行复杂处理。

### 5.3 可靠缓冲与恢复语义

- 已确认事件在接入进程终止后仍必须可继续处理；
- 消费语义按至少一次设计，同一事件编号的重复投递/消费结果幂等；
- 重试有次数、退避和资源上限；无法处理的事件进入权威失败记录/死信，不可静默丢弃；
- 缓冲积压、最老年龄、接收率、拒绝原因、重试、死信和处理水位必须可观测；
- C1 只有“测试问题生成”才视为接入成功；C7 分开展示未收到、已拒绝、已可靠接收、处理中和已生成问题；
- 当前 TDR 目标建议正常容量下 95% 事件 60 秒内可查询、99% 5 分钟内可查询；该目标尚需真实缓冲/处理技术和负载模型验证。

### 5.4 与密钥、环境、用量和平台的关系

- C14 的客户端上报密钥与 B6 私密管理令牌是不同对象；前者只能上报，后者用于获准管理能力；
- 启停、允许来源、允许运行环境和最近使用逐密钥归属；项目网站地址不能自动改变来源策略；
- C15 环境是稳定项目维度；环境创建与逐密钥允许是不同 Command；
- B5/D2 的资源用量与保护策略由服务端权威投影，接入不得让浏览器推导计数或状态；
- 管理平台只能通过公开诊断/用量 Query 和获授权 Command 访问接入能力，不能读取内部缓冲、队列或日志。

### 5.5 尚未确认或尚无正式规格

- 批次/事件大小、批量数量、超时、采样、去重窗口、重试和死信保留数值；
- 峰值吞吐、事件大小分布、容量模型、成本和积压目标；

## 6. 专题四：异步处理、问题聚合与存储

### 6.1 讨论目标与数据流

该专题把已可靠接收事件转为可查询问题、代表样本、源码映射、请求/页面指标、告警实例和数据水位，同时保证重放、重复、保留和删除不会破坏计数或泄露数据。

```text
可靠缓冲事件
→ 清洗/规范化/隐私复核
→ 幂等事件事实
→ 问题指纹与聚合
→ 有限代表样本 / Source Map
→ 分钟桶 → 小时/日桶
→ 查询投影 / 告警评估 / 通知触发
→ 保留、归档、删除
```

### 6.2 事件、问题与代表样本

- 事件是一次发生事实，问题是按稳定指纹聚合的长期对象；两者不能混为一张无限增长明细表；
- 问题维护首次/最近发生、总次数、影响用户估算、状态、负责人、解决版本和再次出现；
- 总次数连续更新，但完整原始事件只保留 PRD 允许的期限和有限代表样本；
- 代表样本优先覆盖首次、最近、再次出现和维度差异，并记录为何被保留/替换；样本不等于完整事件历史；
- 动态规范化只在高置信度下执行，不能把不同根因错误合并；算法/版本变化需要可追溯和可回放评估；
- 问题状态、活动、备注、合并和批量操作作用于问题，不作用于某个样本。

### 6.3 再次出现、发布与 Source Map

- 只有成功部署参与“解决后再次出现”判断；发布与部署身份稳定，环境属于发布上下文；
- Source Map 严格按项目、发布和文件/构建路径匹配，不能跨项目/发布猜测；
- 同摘要上传幂等，不同摘要需要显式替换；旧对象在新对象验证和元数据切换前保持有效；
- 允许对仍在保留窗口内的有限代表样本自动触发有界重解析；不建设无限历史回放或独立用户任务中心；
- Source Map 私密存储、下载重新鉴权，客户端上报密钥永远不能读取。

### 6.4 指标、聚合和告警

- 请求接口身份和页面/路由身份由服务端安全规范化，不由浏览器从有限样本生成；
- 分钟桶同步/近实时更新，小时/日桶按确定规则异步汇总；重复和重放不得重复计数；
- C5 失败率、耗时、慢请求和 C6 LCP/INP/CLS/加载耗时必须返回分母、时间范围、分辨率、计算水位、采样、降级和完整性；
- 空分母/指标不适用是不可计算或 unavailable，不是 0；不同水位不能被前端无说明拼成单一“健康评分”；
- 告警规则定义、当前评估投影、触发实例和实例规则快照分离；数据不足/计算暂停不等于恢复；
- 处理链路必须以业务幂等键防止重复问题计数、通知、告警和删除。

### 6.5 保留、删除与运维

- 保留期、恢复期和永久删除以 PRD 为准；项目归档停止接收/告警，回收站使密钥/令牌失效，永久删除跨平台数据、处理数据和对象续跑确认；
- 删除部分失败不能宣称完成；只保留 PRD 允许的最小非监控安全审计摘要；
- 缓冲、处理任务、失败记录、聚合、代表样本和对象各自需要明确保留/清理策略；
- 队列积压、处理延迟、死信、聚合水位、Source Map 失败、告警暂停和删除停滞必须可观测；
- 恢复测试覆盖重复投递、进程终止、存储故障、对象缺失、重放和跨存储删除确认。

### 6.6 尚未确认或尚无正式规格

- 事件事实、问题、样本、活动、聚合桶、告警、任务和删除编排的逻辑/物理模型；
- 主数据库、时序/分析存储、对象存储、可靠队列、缓存和查询引擎的技术选择；
- 指纹算法/版本、动态归一化阈值、代表样本算法和重新聚合/迁移策略；
- 幂等键、任务状态、租约、分区、并发、重试、死信和重解析执行细节；
- 查询 API、分页/排序、过滤、总量、数据水位和部分失败的机器契约；
- 容量、索引、分区、压缩、保留作业、备份、RPO/RTO、成本和 Runbook；
- 接入/处理系统与管理平台的公开 Query/Command、内部授权和删除传播。

## 7. 专题五：管理平台前后端

### 7.1 正确的约束关系

后端不是简单“参考前端把接口补出来”，前端也不能决定领域事实。正确闭环是：

```text
approved PRD / 权限 / 生命周期
                ↓
五大系统边界与前四专题数据语义
                ↓
后端领域不变量、公开 Query/Command、错误与一致性
                ↕
前端用户任务、页面投影、状态和恢复流程
```

前端设计提供用户需要看到和操作什么；后端根据 PRD/架构决定权威对象、事务、权限和公开能力，再反向约束页面能否实现。二者必须通过机器契约和契约测试闭环，不能让前端能力名冒充接口，也不能让后端内部模型泄露给浏览器。

### 7.2 已批准前端 UX/UI 范围

管理平台共 31 页，并已完成整页、分组、全局导航和全文追踪审计，共 66 项确认记录：

#### A 组：账号与认证 A1—A5

- A1 注册与邮箱验证：账号与个人工作空间原子创建、验证状态、安全重发；
- A2 登录：邮箱/密码最小表单，登录后按有效邀请意图、安全 `returnTo`、工作空间恢复；
- A3 重置密码：请求与设置两个安全子页，统一防枚举结果、一次性意图、成功撤销全部 Session 且不自动登录；
- A4 邀请接受：邮件令牌只建立短期意图，认证后邮箱精确匹配，用户显式接受，成员/权限原子创建；
- A5 账号安全：修改密码、退出和注销独立；唯一组织所有者先转让；A5-001—011 已批准并正式承载，账号机器契约、数据模型、删除编排和 Session/安全 ADR 仍是实施缺口。

#### B 组：组织治理 B1—B8

- B1 按组织分组的工作空间/项目入口，不记录最近访问或自动进入项目；
- B2 单页最小项目创建，唯一操作编号、同步原子创建、超时恢复原结果，成功进入 C1；
- B3 同页“成员/待处理邀请”双标签，成员状态与邀请意图分离，所有权只有所有者转让；
- B4 唯一 IANA 业务时区由所有者/管理员修改并全组织立即生效，真实时间点不变；
- B5 当前周期状态优先用量摘要，包含时区、水位、采样/完整性，不做趋势/排行/收费；
- B6 精确 scope 和有效期，私密令牌原子创建立即激活，明文仅首次成功响应一次性交付；
- B7 所有者/管理员查看统一组织安全审计，项目管理员无独立审计页；
- B8 所有者/管理员查看组织统一回收站；`trash` 可恢复，`deleting` 只读不可恢复。

#### C 组：项目监控与治理 C1—C16

- C1 单页渐进安装/初始化/测试三步，60 秒有界检查；只有测试问题生成才成功，清除测试数据为独立 Command；
- C2 权威状态/原因优先，再展示同口径问题、影响用户估算、活动告警、最近数据和完整性；
- C3 URL 是筛选/搜索/排序/分页权威；个人视图显式保存，当前页选择查询变化即清空；
- C4 问题聚合为主对象，有限代表样本/堆栈/Source Map 从属，活动/备注保持问题级；
- C5 规范化接口列表＋选中详情，只显示服务端失败率/耗时/慢请求时序及水位/采样；
- C6 安全页面列表＋选中详情，只显示服务端 LCP/INP/CLS/加载耗时及适用性/完整性；
- C7 权威接收状态、原因和获授权行动优先，不建设逐事件日志或固定本地诊断进度；
- C8 发布列表＋从属部署记录；管理平台不手工创建发布，只有成功部署参与再次出现；
- C9 选中发布下 Source Map 文件列表＋详情；严格匹配、同摘要幂等、显式替换和有限重解析；
- C10 同页“告警规则/告警实例”双标签，两类对象独立查询/分页；
- C11 指标优先自适应单页表单，前端基础校验与服务端权威组合校验分离；
- C12 当前状态/直接原因/评估证据优先的只读实例详情，历史规则快照与当前规则分离；
- C13 人员唯一行访问清单，分别显示有效权限与组织继承/项目显式来源；
- C14 客户端上报密钥列表＋选中详情，启停/来源/环境/最近使用逐密钥，拒绝来源不自动放行；
- C15 “基本设置/运行环境”双标签且独立版本/Command；环境固定名只查看/创建；网站地址不联动密钥或 SDK；
- C16 项目管理员以上可归档/从归档恢复；只有组织管理员/所有者可移入回收站，B8 恢复权限不变。

#### D 组与跨页面

- D1 账号级统一通知流、全部/未读筛选、逐条已读和后端授权目标；已读不等于业务处理，不做线程/批量/偏好/外部渠道；
- D2 平台完整默认、组织完整覆盖/恢复默认、项目仅资源上限覆盖/清除；展示配置值、来源、生效值和传播状态；
- NAV-A 把认证、账号、工作空间、组织、项目和平台作用域分层；URL、返回、表格、筛选、分页、选择、危险操作、秘密和小屏行为统一；
- AUDIT-A 核对每个元素的业务、权限、公开能力、状态、数据口径和后端缺口；没有 API 的第一版元素保持阻塞而非前端推断。

所有页面按业务需要覆盖 `loading`、`empty`、`error`、`forbidden`、`processing`、`partial`、`stale`、`unavailable`，并按对象增加 `conflict`、`propagating`、`archived`、`trash`、`deleting` 等权威状态。

### 7.3 已批准前端技术栈

| 决策 | 已批准方案 | 核心责任边界 |
|---|---|---|
| FE-STACK-001 | 严格 TypeScript 的 Vue 3 SPA＋Vite | 纯客户端管理应用，不引入 SSR/RSC/BFF；只调用 `platform-api` |
| FE-STACK-002 | Vue Router＋Pinia 领域 Store＋自建请求/缓存层 | URL 是活动查询权威；实现去重、取消、失效、新鲜度、部分/陈旧和 Command 恢复；不使用 TanStack Query |

### 7.4 已批准后端技术栈与服务形态

| 决策 | 已批准方案 | 核心责任边界 |
|---|---|---|
| BACKEND-001 | TypeScript/Node Active LTS、模块化单体 `platform-api`＋独立 `platform-worker`、Fastify、PostgreSQL/Kysely、Zod/OpenAPI | Fastify 只做适配；平台数据库与事件存储隔离；浏览器只用公开 REST/JSON |
| BACKEND-002 | PostgreSQL Transactional Outbox＋Redis/BullMQ＋私有 S3，第一版无独立搜索 | PostgreSQL 是平台业务/Operation/Outbox 权威；BullMQ 只调度；S3 存大对象；不直接双写 Redis |

第一版是两个部署单元而不是按领域微服务。内部按 identity、organization、project-governance、credentials、releases、issues-and-alerts、usage-and-policy、audit、operations 分模块；这些是逻辑职责，不是九个服务。

### 7.5 公开 API 与一致性原则

- REST/JSON 显式主版本、稳定 operationId、OpenAPI 契约优先、RFC 9457 错误；机器 OpenAPI目前不存在；
- Query 返回 `data`、读取/版本/分页/水位/完整性/采样等 `meta` 和仅用于 UI 的 `allowedActions`；
- Command 使用 `Idempotency-Key`、规范化请求摘要、版本/ETag 和显式业务动作；超时通过 Operation Result 或权威对象恢复；
- PostgreSQL 本地不变量在单事务中维护；跨系统使用 Outbox 和状态投影，不用分布式事务；
- `partial`/`stale`/`unavailable` 按分区返回，未知/超时不能伪装成空或 0；
- Browser Session、内部工作负载身份和资源/动作能力令牌分层；下游继续检查自身资源状态；
- 审计、一次性交付秘密、Source Map 和删除都遵守最小披露、幂等和可续跑。

### 7.6 主要未解决项

- BE-GAP-01/02：机器 OpenAPI、请求/响应 Schema、可执行 PostgreSQL 模型、索引/Migration 不存在；
- BE-GAP-03/04：Outbox/BullMQ 租约/并发/重试/死信、Session/Cookie/CSRF/密码/签名/KMS 参数未锁定；
- BE-GAP-05：接入与处理存储系统的正式 Query/Command 缺失，B5、C1—C12、D2 仍无真实依赖；
- BE-GAP-06：对象键、区域、加密、备份、生命周期和孤儿回收需要正式规格；
- BE-GAP-07：A5 产品与安全规则已批准；账号 OpenAPI、数据模型、删除编排和 Session/安全 ADR 仍缺失；
- BE-GAP-08：D2 平台管理员身份、授予/撤销和平台级审计无正式规则；
- BE-GAP-09：邮件供应商、验证/重置/邀请期限、冷却和送达事件未定；
- 前端自建缓存契约、精确依赖版本、API 客户端生成、浏览器真实设备和性能基准尚不存在。

## 8. 专题六：测试、部署和发布

### 8.1 三项关键选择

1. `TD-001=A`：AWS 单一主云；S3/CloudFront 静态 SPA、ECS/Fargate API/Worker、RDS PostgreSQL、ElastiCache、私有 S3；
2. `TD-002=A`：GitHub Actions、短期 OIDC、不可变制品、预发布到生产的同制品晋级、受保护生产审批、expand/contract Migration、ECS 熔断和 SDK npm 独立发布；
3. `TD-003=A`：平衡型 PR/nightly/release 门禁、正式浏览器矩阵、SDK/SPA 量化预算、入口 99.9% 月目标、单区域多 AZ PostgreSQL RPO≤5 分钟/RTO≤60 分钟。

三个方向和完整派生方案 `TDR-DERIVED-001` 已于 2026-07-29 获用户批准。该状态只批准设计；本文仍不得把 CI、AWS、数据库、制品、部署、演练或测试结果写成已经存在。

### 8.2 派生环境与部署方案

- 本地、按需 PR 临时环境、共享预发布和独立生产；至少生产/非生产 AWS 账号隔离；
- 单主区域、生产多 AZ；主区域受用户地域/数据驻留阻塞；
- 管理平台单公共主机推荐 CloudFront：私有 S3 静态源＋`/api/*` ALB 动态源，保持主机限定 Cookie/CSRF；数据接入使用独立主机；
- `platform-api` 私有 ECS Service，Worker 无公网入口；RDS/ElastiCache/S3 私有；
- 推荐 AWS CDK TypeScript，但须部署 ADR；配置/秘密分别进入版本化配置、SSM/Secrets Manager/KMS；
- ECR digest、内容哈希 SPA、npm SemVer、发布清单、SBOM 和来源证明形成可追溯供应链。

### 8.3 测试与 CI

- PR：文档/ADR、架构、类型/Lint/构建、受影响测试、协议/API 契约、SDK exports/体积/Chromium、关键 Playwright、Migration/IaC；
- main：制品、预发布、核心 E2E/Migration；nightly：多引擎、完整 E2E、示例、稳定性/安全/故障；release：完整支持矩阵、性能/负载/积压、恢复、供应链和人工可访问性；
- Core 覆盖率保持 85% 行/80% 分支，其他模块 70%/60%；关键风险不因覆盖率达标免测；
- flaky 不得重跑掩盖，隔离有 Owner/期限；权限、协议、丢失、删除、迁移和宿主破坏测试不能隔离后发布；
- 测试数据合成并去敏，MSW/mock 不替代真实服务/浏览器/存储证据。

### 8.4 兼容、性能与可靠性

- 浏览器：Chrome/Edge/Firefox 最近两个稳定主版本，Safari/iOS Safari 最近两个主版本，Android Chrome 当前/前一稳定，不支持 IE；真实 Safari/移动设备证据仍是缺口；
- WCAG 2.2 AA 作为管理平台目标，自动 axe＋人工键盘/焦点/缩放/屏幕阅读器；
- SDK 包体积与运行开销、SPA JavaScript/Lighthouse/Core Web Vitals 已在专题文档量化，但参考工程尚未建立；
- 数据接入与 platform-api 分别 99.9% 月目标；处理新鲜度目标为正常容量下 p95≤60 秒、p99≤5 分钟；
- PostgreSQL 单区域多 AZ RPO≤5 分钟/RTO≤60 分钟；区域级第一版 RPO≤24 小时/RTO≤8 小时，若要求更高需跨区域架构和 ADR；
- 错误预算耗尽时暂停非关键发布，恢复/修复优先。

### 8.5 发布、迁移、恢复与运维

- 同一 commit 生成不可变制品，预发布验证后由独立生产批准者晋级；
- 数据库 expand → backfill → switch → contract；应用回滚优先，不自动运行破坏性 down Migration；
- API/Worker 重叠版本兼容，Worker 任务负载版本受控；SPA 旧哈希资源保留兼容窗口；
- SDK 坏版本 deprecate＋补丁，不用 unpublish；
- RDS PITR 初始 35 天、每日跨账号/区域恢复点、月度数据库恢复和季度全链路 DR；
- Session Redis 故障失败关闭，数据丢失最多要求重新登录；BullMQ 从 PostgreSQL Outbox 恢复，普通缓存可重建；
- 可观测性覆盖边缘、API、DB、Redis、队列、处理水位、对象、业务不变量和前端；日志/trace 不记录秘密和 PRD 禁止数据；
- 发布前需测试、兼容、备份、迁移、回滚、告警、Runbook、文档和安全证据。

### 8.6 当前阻塞与 ADR 输入

测试/部署文档列出 `TDR-GAP-01—10`：区域/驻留、Monorepo 工具、接入/处理物理技术、机器契约/模型、版本/容量、真实设备、性能基准、安全/邮件参数、产品数据生命周期和运营组织。它们不阻止设计批准，但分别阻止 ADR、planning、实施或发布。

新 ADR 候选包括 AWS/IaC/环境、不可变制品/发布/Migration、浏览器/SDK 公共兼容，以及前后端专题已经识别的技术栈、安全和数据基础设施；日常测试矩阵、版本表、Runbook 和检查表应进入普通文档，不把频繁操作参数全部塞进 ADR。

## 9. 六专题端到端闭环

```text
Monorepo/工程工具
  └─ 约束公共出口、依赖、原子协议变更、测试和制品

event-schema
  ├─ SDK Core/Browser/插件生成并校验标准事件
  ├─ 数据接入再次运行时校验后可靠接收
  └─ 处理/存储只消费受支持版本

SDK → 数据接入 → 可靠缓冲 → 异步处理/聚合/存储
                                  ├─ 问题/样本/Source Map
                                  ├─ 请求与页面指标
                                  ├─ 告警实例/水位/完整性
                                  └─ 公开 Query/Command

管理平台 Vue SPA → platform-api → 平台 PostgreSQL/Redis/S3
                               └→ 接入/处理系统公开能力

测试/部署/发布
  └─ 对上述每个边界提供契约、故障、兼容、性能、恢复和制品证据
```

闭环中的关键语义：

- SDK 发送成功不等于服务端接收；服务端接收成功不等于处理完成；处理完成不等于问题/告警一定生成；每阶段有独立事实；
- 管理平台不读取缓冲、队列或存储内部状态，只消费公开、获授权、带水位/完整性的投影；
- 公共协议是跨系统唯一来源，数据库模型、前端类型和示例不能各自定义协议；
- 测试/发布必须证明边界在重复、失败、回滚、恢复和版本重叠时仍成立；
- 同一 AWS 云、同一 Monorepo 或同一语言不等于逻辑系统可以合并。

### 10.2 新 ADR 候选分组

本文只给出分组，不预占编号：

1. Monorepo 工具、包管理器、任务/缓存和版本发布组合；
2. `event-schema` 具体运行时 Schema 与代码/文档生成组合（若不能由 ADR-005 覆盖）；
3. 数据接入可靠缓冲与接入运行基础设施；
4. 处理/聚合/存储、分析查询、对象和任务基础设施；
5. 管理平台前端技术栈；
6. 管理平台后端运行时、模块化单体/Worker、HTTP/DB/契约链；
7. 平台 Transactional Outbox、Redis/BullMQ 和 S3；
8. Redis Session、CSRF、内部能力令牌和密钥托管；
9. AWS 账号/网络/运行服务、环境隔离与 IaC；
10. 不可变制品、GitHub Actions OIDC、数据库 Migration、生产晋级与回滚；
11. 浏览器、SDK 公共兼容和量化性能承诺（若评审认定属于长期公共兼容决策）。

ADR 拆分原则：同一决策驱动、相同 Owner/评审者、可一起迁移/回滚的内容可以合并；安全、数据、基础设施或公共兼容需要不同专业评审时应拆分。不要把所有技术栈写进一份“大一统 ADR”，也不要为每个小库创建 ADR。

### 10.3 ADR 必备证据

每份 ADR 至少应从本总结抽取：背景、约束/非目标、两至三个真实可行候选、正负影响、长期成本、安全/隐私、兼容、迁移、回滚、验证、重新评估条件、关联 PRD/架构/专题/Issue/PR/测试/文档、决策/实施双状态和评审者。精确工具版本、命令、阈值和 Runbook 若会频繁变化，放入普通正式文档并由 ADR 链接。

## 13. 明确否决或不属于第一版的方向

跨专题已明确排除：

- 多仓库或从第一天微服务/Kubernetes；除非规模、团队、隔离或合规证据改变；
- Core 直接依赖 Browser、插件独立发送/队列、全局单例协作或 shared 绕边界；
- 浏览器持久无限离线队列、未经可靠写入即确认接收、同步完成全部聚合；
- 永久保存完整事件历史、把代表样本当全量、跨发布猜测 Source Map、无限重解析；
- 管理平台直连数据库/队列、浏览器 BFF/SSR/RSC、微服务拆分、独立搜索、JWT Bearer Session；
- 第一版全项目健康评分、趋势/排行仪表盘、通知线程/外部渠道、收费、自定义角色、复杂环境生命周期、用户任务中心；
- 多云/跨区域双活、生产从分支重建、自动破坏性 down Migration、npm unpublish 回滚；
- 用 mock、覆盖率、WebKit 或 axe 单独证明真实集成、Safari 或 WCAG 合规。

这些排除项不是永久禁止。达到各设计文档记录的重新评估条件时，必须通过新需求/ADR/替代文档正式变更，不能在实现中静默引入。

## 14. 推荐的正式化顺序

该顺序用于后续整理，不是 `writing-plans`：

1. 已完成：用户批准测试/部署/发布设计，并确认本总结作为正式化输入；
2. 维护[正式文档索引](../../README.md)和[正式化与实施就绪追踪](../../architecture/formalization-readiness.md)；A5 产品规则已关闭，D2、A5 之外的关键保留/邮件/运营责任继续作为统一阻塞，不在本总结扩展设计；
3. 复审 ADR-001—006，把六专题新增证据并入原提案，按规范完成非作者/领域评审；
4. 建立并评审分组的新候选 ADR：工程工具、前端栈、后端栈、Session/安全、接入/处理数据基础设施、AWS/IaC、发布/迁移；
5. 在相关产品规则和 ADR 收敛后完成 `event-schema` 与事件协议、SDK 公共 API、接入 API/可靠缓冲、处理/存储数据与 Query/Command 规格；
6. 完成平台 OpenAPI、数据模型/Migration、权限/错误/Operation、前端自建缓存契约；
7. 按真实模块创建 README，并补齐测试矩阵、性能基准、兼容、部署、备份恢复、事故/死信/删除和发布文档；
8. 执行一次跨专题追踪审计：PRD → 架构/ADR → 协议/API/模型 → 测试 → 发布/运维；
9. 向用户展示 ADR 列表、正式文档树、全部阻塞、兼容/性能/SLO 和实施边界；只有用户明确批准实施就绪，才可以进入 `writing-plans`。

ADR 与正式规格并非绝对串行：候选 ADR 需要协议/数据/容量原型证据时，可在“设计/验证材料”范围内迭代；但正式实现不能先于 required ADR accepted，机器契约也不能把未决长期选择伪装为既定事实。

## 15. 最终实施就绪审查清单

进入 `writing-plans` 前至少核对：

- [ ] 六专题设计状态与用户批准记录准确；
- [ ] approved PRD/规则冲突为零，产品缺口已决定或明确从第一版移除；
- [ ] required ADR 已 accepted，并具有独立评审、迁移/回滚/验证/重评条件；
- [ ] ADR 决策状态与实施状态分离，索引同步；
- [ ] event-schema、SDK API、接入 API、处理 Query/Command、平台 OpenAPI 是唯一权威且可契约测试；
- [ ] 数据模型、事务/幂等、任务、保留/删除和 Migration 有可执行规格；
- [ ] Monorepo 工具、Node/包/版本/命令、依赖矩阵和制品关系已锁定；
- [ ] AWS 区域、账号、网络、IAM/KMS、服务版本/容量、IaC 和成本边界已批准；
- [ ] 浏览器/框架矩阵、SDK/SPA 性能预算、SLO/RPO/RTO 有真实基准和可验证口径；
- [ ] CI、预发布、生产审批、发布/回滚、备份恢复和事故 Runbook 有 Owner；
