# Aurora 前四个基础专题既有设计批准基线

## 1. 文档定位

本文把用户于 2026-07-28 对前四个基础专题“已有讨论结论”的明确批准固化为仓库内正式记录，避免使用聊天记录代替设计依据。

批准范围严格限定为批准前已经存在于 approved PRD、approved 架构/测试规范、现有设计决策表和 proposed ADR 中，且能够明确追溯的结论。本文不补造没有讨论过的技术选择，不把方向性基线改写成完整实施规格，也不授权代码、项目初始化、基础设施创建或 `writing-plans`。

四个专题为：

1. Monorepo 与工程工具；
2. SDK Core、Browser、插件和框架适配；
3. 数据接入与可靠缓冲；
4. 异步处理、问题聚合与存储。

## 2. 权威性与状态解释

- 第一版业务范围和公共行为继续以 approved 核心 PRD 为唯一产品依据；
- 系统边界、SDK 分层、可靠接收/异步处理、`event-schema` 单一来源和依赖方向继续以 approved 架构规范为准；
- 本文只确认用户认可这些既有设计基线及已有会话决策，不替代上述权威来源；
- ADR-001 至 ADR-006 当前全部为 `proposed / not-started`。用户批准既有专题基线不等于 ADR 完成非作者及必要领域评审，不改变 ADR 状态；
- 只有未来存在的 accepted ADR、正式公共契约和经批准的专题实施规格才能解除相应实施门禁。

## 3. 已批准的既有专题基线

### FOUNDATION-001：Monorepo 与工程工具

已批准范围：

- SDK、服务端、管理平台、公共协议、文档、示例和工程工具位于统一 Monorepo；
- 可部署应用、可复用包、示例、文档和工程工具保持明确一级分类；六份长期规范保留固定根路径；
- 跨包只能使用公开导出，禁止引用其他包的 `src`、`internal` 或私有路径；
- 依赖保持单向，并通过未来的 TypeScript、Lint、包导出、依赖图和 CI 约束执行；
- 同仓库或同部署不允许合并五大系统的逻辑职责。

未包含在本次批准中的内容：

- 包管理器、工作区/任务编排工具、依赖检查工具；
- 统一或独立版本策略、变更记录和发布编排；
- 构建缓存、受影响任务计算、CI 平台和远程缓存；
- Node 版本、锁文件策略、产物仓库和制品签名。

实施门禁：ADR-001、ADR-006 仍须按 ADR 规范完成评审；具体工程工具必须另有正式选择，不能从“统一 Monorepo”推导出某个未批准产品。

### FOUNDATION-002：SDK Core、Browser、插件和框架适配

已批准范围：

- SDK 采用 Core、Browser、采集插件和框架适配分层；Core 环境无关，不直接访问浏览器全局；
- Browser 封装浏览器能力，插件只负责捕获、转换和释放，框架适配只增加框架语义；
- 插件不得自行发送、维护独立队列、绕过统一隐私/采样管道、访问 Core 私有状态或依赖其他插件内部实现；
- SDK 最高优先级是不破坏宿主，必须覆盖异常隔离、重复初始化、完整销毁、代理恢复、资源上限和多实例隔离；
- 第一版使用内存队列、批量发送、事件稳定编号和有限重试，不建设浏览器持久化离线队列；
- 安全默认采集、请求来源边界、URL/错误归一化、匿名标识和禁止采集项以 PRD 为准；
- 事件结构、枚举、协议版本和运行时 Schema 由 `event-schema` 统一管理。

未包含在本次批准中的内容：

- SDK 公共 API 签名、插件接口、环境适配接口和包导出清单；
- 运行时 Schema 具体库、发送协议和批次上限；
- 精确默认配置对象、错误类型和调试接口；
- React/Vue 适配 API、浏览器版本矩阵、SDK 包体积与性能数值；
- 构建、Tree-shaking、发布和兼容迁移方案。

实施门禁：ADR-003、ADR-005、ADR-006 仍须完成规定评审；正式 SDK/协议文档和每个模块 README 仍不存在。

### FOUNDATION-003：数据接入与可靠缓冲

已批准范围：

- 同步接入只执行身份/密钥、来源、环境、大小、协议、运行时 Schema、隐私、去重、采样和限流等必要检查；
- 返回“已接收”前必须完成可靠写入；“已接收”只表示进入可靠缓冲，不表示事件已存储、问题已生成或告警已计算；
- 异步消费者负责后续存储、聚合、Source Map、指标和告警；SDK 不等待这些步骤；
- 事件稳定编号驱动服务端去重和幂等；混合批次采用请求级结果加逐事件结果，单条错误不导致整批失败；
- 永久拒绝不重试，临时失败和明确限频等待使用有界重试；
- 处理失败必须有上限、失败记录或死信，积压、延迟和失败率可观测；
- 接入向导与诊断页必须区分未收到、已收到其他数据、可靠接收、处理中、问题已生成和接入异常。

未包含在本次批准中的内容：

- 正式上报 API、批次 Schema、逐事件错误码和协议版本兼容契约；
- 数据库任务表、消息队列或其他可靠缓冲技术；
- 分区键、顺序、消费并发、租约、可见性超时和重放策略；
- 死信保留/处置、积压阈值、接收与处理 SLO；
- 身份校验、限流和资源策略的物理实现。

实施门禁：ADR-004、ADR-005 仍为 proposed；正式事件协议、接收 API、可靠缓冲和运维设计仍须补齐。

### FOUNDATION-004：异步处理、问题聚合与存储

已批准范围：

- 事件是一次真实发生，问题是相似事件聚合；问题总量持续更新，完整事件只保留有限代表样本；
- 代表样本优先保留首次、最新、再次出现及新版本/环境/浏览器/页面/接口等差异；默认样本上限是服务端配置，不写死在前端；
- 错误聚合只替换高置信度动态值，优先使用 Source Map 后的关键调用栈；自定义 fingerprint 有界并继续接受隐私和服务端校验；
- Source Map 严格按项目、发布和构建文件路径匹配；上传/替换触发有界异步重解析，不跨版本猜测，也不批量重组全部历史问题；
- 生命周期总量和分钟桶同步更新，小时/天桶确定性异步滚动生成，并向查询方暴露更新时间、水位、采样和完整性；
- 问题状态、负责人、再次出现、告警、保留、降级、归档、回收站和永久删除继续遵守 PRD；
- 异步处理必须幂等、有限重试、可观测，并保留失败记录。

未包含在本次批准中的内容：

- 核心数据库、对象存储、搜索、队列和缓存技术；
- 正式物理/逻辑数据模型、索引、分区、事务和并发控制；
- 聚合/计数幂等实现、处理任务状态、重解析调度和告警执行器；
- 查询服务、数据口径 API、存储容量、清理批次和处理 SLO；
- 备份、恢复、灾难恢复和运维 Runbook。

实施门禁：ADR-002、ADR-004、ADR-005 及未来数据库/队列/对象存储等 required ADR 尚未 accepted；已批准后端与测试/部署/发布设计提供方向，但正式数据/任务/运行规格、容量证据和基础设施 ADR 仍须独立收口。
