# Aurora 文档治理与 Agent 开发流程设计

## 1. 目标

本次工作建立 Aurora 的项目级 Agent 开发约束，同时保持现有六份规范文档的长期连续性。

完成后必须满足：

- 产品正式名称统一为 `Aurora`；
- 现有六份规范文档继续作为正式、长期维护的权威来源；
- 六份规范文档不删除、不移动、不重命名，也不复制出替代版本；
- 新建 `AURORA_RULES.md`，使新对话只阅读该文件即可恢复项目开发上下文；
- 新建根目录 `AGENTS.md`，将读取顺序、开发流程、禁止事项和验证要求转化为项目级强制约束；
- 后续规则变更只能追加，不能删除、覆盖或静默改变历史原则；
- 六项初始架构决策形成正式 ADR 文件，但初始状态保持 `proposed`、实施状态保持 `not-started`；
- 文档名称、链接、Markdown、章节编号、状态和异步处理语义通过自动检查验证。

## 2. 权威文档边界

以下六份文件是不可替代的长期规范载体：

1. `Auroa-PRD-业务逻辑汇总-v2.1-核心业务定稿版.md`
2. `Aurora 架构规范.md`
3. `Aurora 代码规范.md`
4. `Aurora 测试规范.md`
5. `Aurora 文档规范.md`
6. `Aurora ADR 规范.md`

对这六份文件执行以下保护规则：

- 保持原路径和原文件名；
- 不创建内容相同的“新版”“最终版”或迁移副本；
- 不使用其他文档替代其领域权威性；
- 允许修复错别字、编号、链接、Markdown 格式和其他不改变规则语义的问题；
- 任何校正都必须在对应文件末尾追加维护记录；
- 任何新增、废弃或替代规则都必须通过追加记录表达。

PRD 文件名中的 `Auroa` 作为历史固定路径保留。PRD 正文、文档标题、示例、规则说明及所有新文件中的产品名称统一为 `Aurora`，并在 PRD 顶部注明历史文件名保留原因。

## 3. 规则层级

项目内文档按照以下职责协作：

1. `AGENTS.md` 是 Agent 自动发现的项目级执行入口，规定必须执行的读取、判断、开发、验证和交付动作。
2. `AURORA_RULES.md` 是规则体系最高级入口和单文件开发上下文，汇总当前项目状态、核心边界、Agent 工作流和正式文档索引。
3. 六份长期规范分别是产品、架构、代码、测试、文档和 ADR 领域的详细权威来源。
4. `accepted` ADR 是具体重大决策的正式依据；`proposed` ADR 只能用于评审，不得约束正式实现。
5. 模块 README、API、协议、发布和运维文档在后续实现阶段补充，不能与以上规则冲突。

Agent 发现不同文件存在真实冲突时，不得自行选择最方便的规则，也不得开始受冲突影响的实现。Agent必须记录冲突位置、影响范围和可选处理方式，并请求项目负责人决策。决策完成后，通过追加式规则记录消除冲突。

## 4. 追加式维护协议

### 4.1 初始基线

本次整理完成时，六份规范各自在文件末尾追加“规则维护与追加记录”，并登记当前内容为初始基线。初始基线记录至少包含：

- 基线编号；
- 生效日期；
- 文档状态；
- Owner；
- 维护方式；
- 本次非语义校正摘要。

### 4.2 历史保护

初始基线形成后：

- 禁止删除历史规则；
- 禁止直接改写历史原则；
- 禁止通过修改原段落静默改变规则含义；
- 禁止复用已有规则编号表达不同含义；
- 禁止删除被废弃或被替代规则；
- 禁止仅更新 `AGENTS.md` 或 `AURORA_RULES.md` 而不更新对应领域规范。

### 4.3 允许的非语义校正

以下修改可以直接修正文档正文，但必须追加维护记录：

- 产品名、错别字和标点；
- 无语义变化的章节编号；
- Markdown 围栏、缩进和表格格式；
- 已失效的内部相对链接；
- 明确错误的关联编号；
- 不改变规则含义的示例格式。

### 4.4 新规则追加格式

每条规则变化追加在对应领域文档末尾，格式固定为：

```markdown
### RULE-YYYYMMDD-NNN：规则标题

- 状态：proposed | approved | deprecated | superseded
- 提出日期：YYYY-MM-DD
- 生效日期：YYYY-MM-DD 或 none
- Owner：模块或角色
- 影响范围：
- 关联规则：
- supersedes：none 或旧规则编号
- 变更原因：
- 新增规则：
- 兼容与迁移说明：
- 验证方式：
```

只有 `approved` 追加项属于当前正式规则。`proposed` 不约束正式开发。新规则替代旧规则时必须声明 `supersedes`，旧规则正文和历史状态继续保留。

### 4.5 复查记录

六份长期规范的 front matter 记录本次基线的 `last-reviewed`。后续复查不得为了更新日期而覆盖历史元数据，而是在文件末尾追加带日期的复查记录。`AURORA_RULES.md` 的当前文档索引应指出最近一次复查记录。

## 5. `AURORA_RULES.md` 设计

`AURORA_RULES.md` 必须是自包含的开发上下文文件。新 Agent 只阅读该文件，应能够回答：

- Aurora 是什么、服务谁、第一版解决什么问题；
- 当前项目处于什么阶段；
- 第一版必须做什么、明确不做什么；
- 系统由哪些边界组成，依赖方向如何；
- SDK 如何采集、过滤、采样、排队和上报；
- 数据接收成功代表什么，后台异步处理何时完成；
- 问题如何聚合、处理、解决和再次出现；
- 哪些安全、隐私和宿主隔离规则不可绕过；
- 代码、测试、文档和 ADR 的最低要求；
- Agent 接到任务后必须执行什么流程；
- 当前哪些文档和 ADR 有效；
- 规则如何追加和长期维护。

文件至少包含：

1. 项目标识与正式名称；
2. 当前阶段与上下文快照；
3. 产品核心闭环；
4. 第一版范围与非目标；
5. 五大系统及 SDK 分层；
6. 事件和数据处理主流程；
7. 关键业务规则摘要；
8. 不可违反的 SDK、安全和隐私规则；
9. 编码质量基线；
10. 测试和完成标准；
11. 文档与 ADR 治理；
12. Agent 端到端开发流程；
13. 当前必读文档索引；
14. 当前 ADR 状态；
15. 追加式规则维护协议；
16. 规则追加记录。

`AURORA_RULES.md` 可以总结六份规范，但不得声明自己取代六份规范。Agent 实际开始开发前仍须完整阅读六份规范。

## 6. `AGENTS.md` 设计

根目录 `AGENTS.md` 适用于整个 Aurora 工作区及所有后续子目录。

它必须强制 Agent：

- 新对话先读取 `AURORA_RULES.md`；
- 在首次修改代码或正式文档前完整读取六份长期规范；
- 读取与任务相关的已批准 ADR、模块 README、API 和协议文档；
- 先确认任务属于 PRD 第一版范围，禁止自行扩展后置功能；
- 先判断是否需要 ADR；需要 ADR 时只能创建 `proposed` 草案，未批准不得实施重大决策；
- 保持五大系统、SDK 分层、事件协议和单向依赖；
- 对外部输入执行运行时校验；
- 保护宿主页面，禁止 SDK 内部错误冒泡、重复监听、递归上报和无限队列；
- 按风险补充单元、集成、契约、真实浏览器或端到端测试；
- Bug 修复原则上先建立可复现的回归测试；
- 在完成前运行与修改范围匹配的验证命令并检查实际输出；
- 同一变更同步更新受影响文档；
- 对规则文件只追加，不删除、不覆盖历史原则；
- 发现冲突、缺少批准或存在重大范围歧义时停止相关实施并报告。

`AGENTS.md` 应保持可执行、明确和紧凑，不复制六份规范的全部正文。它需要包含关键禁止项，以确保即使工具只自动加载 `AGENTS.md`，Agent 也不会在读取完整规范前进行危险修改。

## 8. 初始 ADR

在 `docs/adr/` 下创建：

- `ADR-001-use-monorepo.md`；
- `ADR-002-five-system-boundaries.md`；
- `ADR-003-sdk-plugin-architecture.md`；
- `ADR-004-asynchronous-event-processing.md`；
- `ADR-005-event-schema-source-of-truth.md`；
- `ADR-006-one-way-dependencies.md`。

每份 ADR 必须包含至少两个真实候选方案、正反影响、实施约束、迁移、回滚、验证和重新评估条件。初始状态统一为：

```text
决策状态：proposed
实施状态：not-started
```

这些 ADR 用于把现有架构原则转化为可独立评审的决策提案，不删除、不缩减也不替代架构规范。未经后续明确评审，不得将其改为 `accepted`。

## 9. 验证设计

实施完成后执行只读检查，至少验证：

- 六份原始规范文件路径全部存在；
- 六份规范没有迁移副本；
- 除历史 PRD 文件名说明外，正文和新文件不再使用产品名 `Auroa`；
- `AURORA_RULES.md` 和 `AGENTS.md` 存在；
- 六份规范均存在追加式维护基线；
- 六份 ADR 均存在且状态为 `proposed`、实施状态为 `not-started`；
- 所有 Markdown 相对链接指向存在的文件；
- 所有围栏代码块成对闭合；
- PRD 不存在已知重复章节编号；
- 文档规范中的 5.7 至 5.10 能被识别为正式标题；
- `AURORA_RULES.md` 包含项目上下文、读取顺序、Agent 工作流和当前文档索引；
- `AGENTS.md` 明确禁止在未读取规则或缺少 ADR 批准时实施受影响变更。

当前目录不是 Git 工作区，因此本轮不能执行提交、分支或 PR 操作。所有交付以文件系统内容和验证报告为准。

## 10. 非目标

本次不实施业务代码，不选择框架、数据库、队列或部署平台，不将任何 `proposed` ADR 提升为 `accepted`，也不新增 PRD 第一版之外的产品能力。
