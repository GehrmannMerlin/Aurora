# ADR-001：使用统一 Monorepo

## 背景

Aurora 第一版同时包含浏览器 SDK、框架适配、数据接入、异步处理、管理平台、公共事件协议、示例和文档。这些部分频繁共享协议、类型、测试样本和发布约束。

仓库策略会长期影响原子变更、版本管理、依赖可见性、CI、发布和团队协作，因此需要独立记录取舍。

## 决策驱动因素

- event-schema 需要被 SDK、接入和处理共同使用；
- 协议变更需要在一个变更中同步代码、测试和文档；
- 跨包依赖必须可检查；
- 多个 SDK 包需要统一版本和构建规则；
- 第一版团队规模和部署复杂度有限；
- 六份长期规范必须保持固定根路径；
- 后续仍应允许应用独立构建和发布。

这里的“独立构建和发布”是制品与验证边界，不决定统一版本、独立版本或发布列车策略；版本与发布方式必须另行决策。

## 候选方案

### 方案 A：统一 Monorepo

将应用、包、示例、文档和工具放入同一仓库，以 apps、packages、examples、docs 和 tooling 划分。

优点：

- 协议和消费者可以原子修改；
- 依赖图、类型和契约测试可以统一检查；
- 新对话只需恢复一个仓库上下文；
- 构建、Lint、测试和版本策略可以复用；
- 更适合第一版跨模块快速迭代。

缺点：

- CI 和缓存需要按受影响范围优化；
- 仓库扩大后权限和发布边界需要额外治理；
- 不加约束时容易跨包访问内部实现；
- 工具配置和工作区依赖需要统一维护。

### 方案 B：每个系统独立仓库

SDK、服务端、管理平台和公共协议分别维护仓库，通过发布包和版本依赖协作。

优点：

- 仓库权限和发布节奏天然隔离；
- 单仓库体量较小；
- 不同团队可以独立选择部分工程工具。

缺点：

- 协议变更需要跨仓库协调；
- 容易出现 SDK、服务端和文档版本漂移；
- 契约样本和类型可能复制；
- 第一版需要过早建设跨仓库发布与兼容流程；
- 新对话恢复完整上下文成本更高。

### 方案 C：SDK Monorepo 与平台仓库分离

SDK、插件和协议在一个仓库，服务端和管理平台在另一个仓库。

优点：

- SDK 相关原子变更仍较容易；
- 平台代码与发布权限可以隔离；
- 仓库规模介于前两者之间。

缺点：

- event-schema 仍需跨仓库发布；
- 端到端链路和文档存在双重来源风险；
- 第一版增加版本编排，但未获得明显业务收益。

## 最终决策

决定选择方案 A：统一 Monorepo。

选择依据是 Aurora 第一版跨模块协议协作频繁，而团队和仓库规模尚未证明需要物理拆分。本决策不批准具体包管理器、任务编排器、缓存或版本发布策略，也不表示 Monorepo 已经建立。

六份长期规范继续保留在仓库根目录，作为 Monorepo 目录规则的明确例外。

## 结果与影响

### 正面影响

- 协议、实现、测试和文档可以原子评审；
- 更容易建立统一依赖检查和契约测试；
- 减少第一版跨仓库发布成本；
- Agent 能在一个工作区恢复完整上下文。

### 负面影响与代价

- 必须投资受影响构建、缓存和依赖约束；
- 需要明确包公开导出和私有目录；
- 仓库权限不能完全替代模块权限；
- 不受控的跨包引用会削弱系统边界。

### 未解决问题

- 具体包管理器和 Monorepo 工具尚未决定；
- 独立版本或统一版本策略尚未决定；
- CI 缓存和发布编排尚未决定。

## 实施约束

- 可部署应用进入 apps；
- 可复用包进入 packages；
- 示例进入 examples；
- 新增长期设计进入 docs；
- 工程工具进入 tooling；
- 六份长期规范保持现有根路径；
- 跨包只能通过公开入口；
- 禁止访问其他包的 src 或 internal；
- CI 必须检查循环依赖、未声明依赖和私有引用。

## 迁移方案

当前仓库主要是规范文档。ADR accepted 后，根据实际技术选型建立目录和工作区配置；每增加一个模块，同时增加 README、公开入口、依赖声明和测试。无需移动六份长期规范。

## 回滚方案

在大规模代码产生前，如果评审拒绝该方案，可以撤回本 ADR 并选择多仓库或混合方案。已经存在的六份规范和 ADR 历史继续保留。若实现后再拆仓，必须创建新 ADR、制定包和历史迁移方案，禁止静默拆分。

## 验证方式

- 仓库一级目录符合批准结构；
- 跨包导入只使用公开入口；
- 依赖检查无循环和反向依赖；
- 协议变更可在单一 PR 中同步消费者、契约测试和文档；
- 各应用和包可独立构建、测试和发布。

## 重新评估条件

- 仓库规模导致 CI 或开发体验持续不可接受；
- 权限隔离不能通过目录和流程满足；
- 多个团队需要完全独立发布和生命周期；
- 单仓库工具不再维护；
- 法规或安全要求强制物理隔离。
