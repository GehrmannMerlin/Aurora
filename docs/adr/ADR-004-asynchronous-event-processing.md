# ADR-004：采用可靠接收与异步事件处理

## 元数据

- 状态：accepted
- 日期：2026-07-27
- Owner：backend
- 适用范围：数据接入、可靠缓冲、异步处理、存储、聚合、Source Map 和告警

- 关联技术方案：[Aurora 架构规范](<../../Aurora 架构规范.md>)
- 关联 Issue：none
- 关联实现 PR：none
- 替代 ADR：none
- 被替代 ADR：none

- 评审状态：非作者及所需领域评审已通过

## 背景

事件上报请求需要在浏览器页面中快速完成，但 Source Map、错误分组、性能聚合、存储和告警可能耗时或暂时失败。若所有处理都在同步请求中完成，SDK 延迟和服务端失败面会扩大；若未经校验直接返回成功，平台又可能接收不可恢复的非法或丢失数据。

## 决策驱动因素

- SDK 上报不能长时间占用宿主资源；
- 接收成功的数据不能因进程重启丢失；
- 处理失败需要重试、幂等和失败记录；
- 接入向导需要区分“已接收”和“问题已生成”；
- 队列积压和处理延迟必须可观测；
- 第一版不能为了未来规模引入过重基础设施。

## 候选方案

### 方案 A：同步必要校验并可靠缓冲，后续异步处理

同步阶段完成鉴权、来源、环境、大小、协议、Schema、隐私、去重、限流和必要采样，然后写入可靠缓冲并快速返回。后台异步执行存储、Source Map、聚合、指标和告警。

优点：

- 上报延迟可控；
- 接收和处理失败语义清楚；
- 耗时能力可以独立重试和扩展；
- 队列削峰保护存储；
- 接入状态可以准确展示等待处理。

缺点：

- 需要可靠缓冲和消费幂等；
- 数据写入到可查询之间存在最终一致性；
- 必须监控积压、死信和处理延迟；
- 用户界面需要区分接收与完成。

### 方案 B：在上报请求中同步完成全部处理

同步完成校验、存储、Source Map、问题聚合、指标和告警后返回。

优点：

- 返回成功时数据立即可查询；
- 不需要队列和消费者；
- 处理链路表面简单。

缺点：

- 请求延迟和超时不可控；
- Source Map 或存储故障会阻塞上报；
- 重试容易重复聚合和告警；
- 高峰流量直接冲击全部后端；
- SDK 页面退出前难以等待完成。

### 方案 C：先返回成功，再把原始请求放入易失内存队列

接入层不持久化，直接把事件放入进程内存并返回。

优点：

- 实现快；
- 响应延迟最低；
- 不依赖外部队列。

缺点：

- 进程重启会丢失已确认数据；
- 无法提供可靠接收语义；
- 横向扩展和积压管理困难；
- 不符合监控数据正确性目标。

## 最终决策

决定选择方案 A：同步必要校验和可靠接收，复杂处理异步执行。

本决策只接受“同步必要校验并可靠缓冲、复杂处理异步执行”的行为语义。数据接入与处理的物理缓冲技术仍需独立评审；管理平台已批准的 PostgreSQL Outbox＋Redis/BullMQ 不自动适用于该边界。

## 结果与影响

### 正面影响

- SDK 可以快速获得明确接收结果；
- 耗时处理与接入故障隔离；
- 支持有限重试、幂等和死信；
- 可以按积压独立扩展处理能力；
- 接入诊断和数据可信度更清楚。

### 负面影响与代价

- 引入最终一致性；
- 需要事件状态、幂等键和消费者治理；
- 需要监控缓冲可用性、积压和失败率；
- 用户可能误解“已接收”为“已可查询”。

### 未解决问题

- 第一版可靠缓冲的具体技术；
- 消费并发和顺序策略；
- 死信保存和人工处理方式；
- 处理延迟服务目标。

## 实施约束

- 接收成功前必须完成必要鉴权、限制、运行时校验和可靠写入；
- 返回成功不等待 Source Map、分组、聚合和告警；
- 同一事件编号的重复消费结果幂等；
- 一批单条失败不导致整批回滚；
- 失败重试次数和退避有上限；
- 无法处理事件进入失败记录或死信；
- 队列积压、处理延迟和失败率可监控；
- SDK 不重试永久拒绝；
- 接入向导轮询异步结果，不要求用户重复发送测试事件。

## 迁移方案

ADR accepted 后先定义接收结果、事件状态和幂等编号，再选择最小可靠缓冲。实现接入写入、消费者、失败记录和监控，最后连接存储、问题聚合和告警。接入成功测试必须覆盖从可靠接收到问题生成。

## 回滚方案

如果异步处理上线失败，可暂停消费者并保留缓冲数据，回滚消费者版本后继续处理。不得通过返回成功后丢弃数据来降级。若决定回到同步模型，必须创建新 ADR 并重新定义 SDK 和接入语义。

## 验证方式

- 接收成功后强制重启进程，事件仍可处理；
- 重复投递不重复创建事件、问题计数或告警；
- Source Map 和聚合延迟不增加接入响应时间；
- 消费失败按上限重试并进入失败记录；
- 队列积压和处理延迟有监控；
- 接入页面正确区分已接收、处理中、成功和失败；
- 端到端测试证明测试问题最终生成。

## 重新评估条件

- 处理延迟长期超过产品可接受范围；
- 缓冲成本或运维复杂度显著超过收益；
- 事件规模需要分区、顺序或流处理能力；
- 数据法规要求改变持久化边界；
- 现有可靠缓冲停止维护或无法扩展。
