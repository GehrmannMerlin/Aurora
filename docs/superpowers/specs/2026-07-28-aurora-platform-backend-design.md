# Aurora 管理平台后端领域、公开 API 与技术栈设计

## 1. 文档定位

本文是 Aurora 第一版管理平台后端专题的工作设计文档，同时收口领域模型、公开 API/Command 和后端技术栈。本文以 approved PRD、approved 架构规则、前四专题批准基线、已批准前端 UX/UI 和前端技术栈为输入，不允许后端设计反向覆盖产品与用户流程。

本文已经完成 `brainstorming` 并获得用户整体批准。批准使本文成为已批准测试/部署/发布设计、正式文档和机器契约的当前输入，但不授权编写代码、初始化服务、创建数据库或基础设施、修改 ADR 状态或进入 `writing-plans`。机器可读 OpenAPI、最终字段名、路径、枚举和可执行数据模型仍不存在。

## 2. 目标、非目标与权威边界

### 2.1 目标

- 为 A1—D2 共 31 个已批准页面提供可追溯的公开 Query/API 与 Command 能力；
- 明确账号、组织、项目、权限、密钥、令牌、发布、告警、通知、资源策略和生命周期等领域边界；
- 定义重新鉴权、事务、幂等、并发、审计、错误、不确定结果和异步状态的一致规则；
- 为统计和图表提供服务端权威来源、计算口径、更新时间、水位、采样、降级、完整性和空值语义；
- 选择第一版可维护的后端主运行时、HTTP 适配、数据库访问、契约、后台任务及必要基础设施；
- 明确需要新增或修订 ADR 的高迁移成本选择和全部实施阻塞。

### 2.2 非目标

- 不设计 PRD 第一版之外的收费、企业治理、外部通知、值班、复杂审批、Session Replay、高级查询或 AI 能力；
- 不把管理平台后端与数据接入、数据处理和存储合并为一个逻辑系统；
- 不为每个领域拆独立微服务，不建设通用工作流、事件总线或独立任务中心；
- 不在设计阶段锁定依赖补丁版本、云厂商、部署平台、机器规格或量化 SLO；
- 不虚构仓库中不存在的 API、数据库表、队列、服务或实现状态。

### 2.3 权威关系

- 第一版业务范围与领域不变量以 approved PRD 为唯一产品依据；
- 五大系统边界、单向依赖、可靠接收与异步处理以 approved 架构规范为准；
- 前端设计提供用户任务、所需投影、Command、状态和错误恢复需求，不决定后端内部实现；
- 管理平台浏览器只调用正式公开 `platform-api`，不得访问数据库、队列、处理存储私有接口或内部能力令牌；
- ADR-001 至 ADR-006 仍是 `proposed / not-started`，本文不改变其效力。

## 3. 已确认关键决策

### BACKEND-001：后端主运行时与服务形态

用户选择方案 A：采用严格 TypeScript 的 Node.js 模块化单体 `platform-api` 加独立 `platform-worker`，使用 Fastify、PostgreSQL、Kysely 和 Zod/OpenAPI 契约链。

| 维度 | 已确认结论 |
|---|---|
| 运行时 | Node.js；实施锁定时选择仍受支持的 Active LTS，并使用严格 TypeScript 编译与类型检查，不把运行时类型剥离当成类型检查 |
| API 形态 | `platform-api` 是一个按领域模块化的可部署应用；第一版不按领域拆微服务，也不增加浏览器 BFF |
| 后台执行 | `platform-worker` 是独立进程/部署单元，消费获准的持久任务；不向浏览器暴露业务 API |
| HTTP 适配 | Fastify 仅负责 HTTP、路由、请求上下文、限流挂点、序列化与传输层错误映射；领域和应用层不得依赖 Fastify 类型 |
| 平台业务数据 | 使用独立逻辑 PostgreSQL 平台数据库和最小权限数据库角色，不与事件明细/聚合存储共享表或私有模型 |
| 数据访问 | 使用 Kysely 表达类型化 SQL；版本化 SQL Migration 是数据库结构的权威变更记录，应用启动不得隐式改表 |
| 公开契约 | REST/JSON、OpenAPI 契约优先、RFC 9457 问题详情；使用 Zod 4 系列 Schema 生成或校验 JSON Schema/OpenAPI，具体 `zod`/`zod/mini` 入口不作为用户级问题 |
| 浏览器边界 | Vue SPA 只消费正式 `platform-api`；不共享数据库模型、Kysely 类型、领域实体或内部能力令牌 |
| 跨系统边界 | `platform-api` 只能通过其他系统的公开服务接口组合监控数据，不能直连接入/处理队列或其私有数据库 |

选择理由：第一版主要复杂度来自业务权限、事务、公开契约、异步状态和数据解释，而不是极限 CPU 计算。该方案与已批准 TypeScript 前端和现有会话设计最一致，能以两个明确部署单元控制运维成本，同时保留领域隔离和未来按证据拆分的路径。

已知代价：TypeScript 类型不能代替运行时校验、数据库约束和权限检查；CPU 密集处理不得占用 API 事件循环；模块边界必须由公开出口、依赖规则、契约测试和架构检查强制执行。

### BACKEND-002：支撑基础设施组合

用户选择方案 B：使用 PostgreSQL Transactional Outbox＋Redis/BullMQ＋私有 S3 兼容对象存储；第一版不引入独立搜索服务。

| 责任 | 已确认边界 |
|---|---|
| 原子提交 | 领域状态、审计、幂等/操作记录和需要异步执行的 Outbox 记录在同一 PostgreSQL 事务中提交；API 不在事务内直接向 Redis 双写 |
| Outbox Relay | 独立 Relay 从 PostgreSQL 读取待投递记录并幂等发布到 BullMQ；发布成功后记录投递事实，进程崩溃可以安全重试 |
| 任务执行 | BullMQ/Redis 负责等待、延迟、优先级、重试和 Worker 领取；投递与执行语义按至少一次设计，所有处理器必须以业务幂等键保护副作用 |
| 权威状态 | PostgreSQL 始终是领域状态、操作结果和 Outbox 的权威来源；BullMQ 状态只用于执行调度，不直接成为公开业务状态 |
| Redis 缓存 | 只缓存可丢弃、可重建、具备明确作用域/版本/TTL/失效规则的读取投影；权限、允许操作、秘密、危险操作结果和删除状态不得仅依赖缓存授权 |
| Redis 故障 | 已提交 Outbox 继续保留并积压，Relay 有界重试；API 不因 Redis 客户端无限等待，公开结果根据领域事务事实返回确定结果或明确的异步延迟/不可用状态 |
| 对象存储 | Source Map 等大对象保存在私有 S3 兼容对象存储；数据库保存摘要、大小、内容类型、对象引用、业务归属、版本和生命周期元数据 |
| 对象访问 | 浏览器只能通过公开 API 获得短期、单对象、单动作的上传/下载意图；不存在永久公开 URL，服务端在发放和完成确认时重新鉴权并校验摘要/大小 |
| 搜索 | 第一版不部署 OpenSearch/Elasticsearch；账号、组织、项目、成员、通知等平台数据使用 PostgreSQL 索引查询，监控问题/事件搜索由数据处理与存储系统的公开 Query 负责 |

该组合比 PostgreSQL-only 多一个 Redis/BullMQ 运行依赖，但获得成熟的延迟任务和重试调度。为避免引入双写错误，BullMQ 不能取代 Transactional Outbox；为避免缓存权限漏洞，Redis 不能成为授权或生命周期的唯一依据。

第一版管理任务包括邮件发送请求、通知生成、资源策略传播、Source Map 后续任务触发、删除/清理编排和必要重试。它不承载 SDK 监控事件接入、原始事件缓冲或高吞吐聚合管道。

专用搜索服务保持明确排除，只有当数据处理系统或 PostgreSQL 查询出现经测量且无法通过索引、分区、查询投影解决的搜索瓶颈，并具备索引一致性、删除传播和运维方案时，才通过新 ADR 重新评估。

### BACKEND-003：Session 权威存储与跨系统授权

用户选择方案 B：Redis 保存不透明服务端 Session 的权威活动状态；PostgreSQL 保存账号、安全版本和必要审计事实；内部服务调用使用短期、受 audience/resource/action 约束的能力令牌，不转发浏览器 Cookie。

| 责任 | 已确认边界 |
|---|---|
| 浏览器凭据 | 使用高熵随机、无业务含义的不透明 Session ID；只通过 `Secure`、`HttpOnly`、无 `Domain` 的主机限定 Cookie 发送，不进入 URL、localStorage、日志或前端持久 Store |
| Session 权威 | 活动 Session、空闲/绝对期限、CSRF 绑定材料、轮换与撤销状态由 Redis 权威保存；Redis 数据丢失或不可用时受保护请求失败关闭，不从 PostgreSQL 猜测恢复仍有效 Session |
| 账号权威 | 账号状态、密码摘要、安全版本和影响 Session 的持久安全事实保存在 PostgreSQL；Session 只证明当前认证，不固化组织/项目角色或允许操作 |
| Redis 隔离 | Session 存储必须与 BullMQ 和普通缓存使用独立凭据、命名空间、容量/淘汰和监控策略；生产部署需要故障与资源隔离，具体实例拓扑归入部署专题 |
| 重新鉴权 | 每个 Command 按当前 PostgreSQL 成员关系、资源生命周期和业务规则重新鉴权；Redis Session 或缓存命中不能授权已被移除的成员或已归档/删除资源 |
| CSRF | 有状态应用使用与 Session 绑定的同步令牌；令牌通过安全 Session Query 返回并由 SPA 在非安全方法的自定义 Header 中发送，同时校验 Origin/Fetch Metadata；令牌不进入 URL 或日志 |
| 密码 | 使用 Argon2id 和每密码唯一盐；具体内存、迭代、并行度及是否使用独立 Pepper 由安全基准、密钥管理和部署能力正式确定 |
| 内部调用 | `platform-api` 使用工作负载身份连接下游，并为单次调用签发短期能力令牌；令牌限定目标服务、资源、动作、调用主体和操作关联，不包含浏览器 Cookie、密码、完整邮箱或无关角色列表 |
| 下游校验 | 下游同时校验工作负载身份、令牌签名、签发方、受众、有效期、资源和动作，并继续执行自身资源状态与数据边界校验；能力令牌不是绕过领域规则的管理员通行证 |
| 撤销与失败 | 用户 Session 可立即从 Redis 撤销；内部能力令牌依靠极短期限、密钥轮换和拒绝旧安全版本控制窗口，不提供长期刷新令牌 |

该方案接受 Redis 成为认证关键基础设施的成本：必须启用符合安全目标的持久化、复制、故障转移、禁止淘汰和恢复演练。Redis 故障时受保护请求以 `503 unavailable` 失败关闭，不能伪装为“用户未登录”，也不能降级为跳过 Session 校验。

PLAT-005 的邮箱密码、Argon2id、不透明 Session、HttpOnly Cookie、CSRF 和不使用浏览器 Bearer Token，以及 PLAT-008 的短期受限内部能力令牌，均由 BACKEND-003 在设计层复核确认；精确期限、Cookie SameSite 策略、密码数值、签名算法、密钥托管和工作负载身份传输仍须安全/部署评审，不作为新的产品功能。

### 已确认的模块化单体内部边界

`platform-api` 与 `platform-worker` 可以复用纯领域、应用用例和公开契约包，但不能通过一个全局容器共享任意可变状态。建议领域模块至少按以下职责分区，最终包名和目录不在本阶段锁定：

- identity：账号、邮箱验证、密码、Session 和账号生命周期；
- organization：组织、成员、邀请、角色、所有权和业务时区；
- project-governance：项目、环境、成员来源、设置、归档、回收站和删除；
- credentials：客户端上报密钥与私密管理令牌，二者使用不同能力模型；
- releases：发布、部署、Source Map 元数据和获授权的处理任务投影；
- issues-and-alerts：问题协作 Command、告警规则、告警实例和通知；
- usage-and-policy：资源用量投影、平台/组织/项目策略及传播状态；
- audit：组织安全审计和未来经正式规则授权的平台级审计；
- operations：幂等记录、操作结果和后台任务恢复，不成为面向用户的独立任务中心。

这些是职责边界，不表示创建九个服务。模块间只能调用公开应用接口；跨模块事务必须由明确用例拥有，不能让 HTTP handler 直接拼接多模块表写入。

## 4. 领域边界与权威数据所有权

| 领域/数据 | 权威所有者 | 持久化与访问边界 | 关键不变量 |
|---|---|---|---|
| 账号、密码、安全版本、验证/重置意图 | identity | 平台 PostgreSQL；秘密只存摘要 | 邮箱规范化唯一；外部响应防枚举；安全意图短期、单用途、可撤销 |
| 活动 Session 与 CSRF 绑定 | identity | 隔离的 Redis Session 存储 | 不透明、高熵、服务器端状态；Redis 故障失败关闭；不承载角色权威 |
| 组织、成员、邀请、所有权、业务时区 | organization | 平台 PostgreSQL | 每个组织恰有一个所有者；角色变更与邀请接受原子；时区为有效 IANA 值 |
| 项目、环境、显式成员、设置、生命周期 | project-governance | 平台 PostgreSQL | 项目创建原子生成默认环境/密钥；环境身份稳定；归档、回收站、删除状态机不可跳步 |
| 客户端上报密钥 | credentials | 平台 PostgreSQL 保存安全摘要与策略元数据 | 只允许上报；逐密钥来源/环境/启停；与私密令牌彻底分离 |
| 私密管理令牌 | credentials | 平台 PostgreSQL 只保存摘要、scope、有效期和安全元数据 | 明文只在创建成功响应出现一次；精确 allowlist scope；撤销不可逆 |
| 发布、部署、Source Map 元数据 | releases | 平台 PostgreSQL；二进制位于私有 S3 兼容存储 | 发布/部署身份稳定；Source Map 严格按项目/发布/文件路径匹配；摘要幂等 |
| 问题、事件样本、接口/页面指标、接收状态 | 数据处理与存储系统 | 只通过其公开 Query/Command；平台不得跨库读取 | 总量与有限样本分离；水位/采样/完整性随结果返回 |
| 问题状态、负责人、活动、备注、合并 | 数据处理与存储系统 | platform-api 重新鉴权后使用短期能力令牌调用公开 Command | 问题级版本与幂等；普通活动不复制为全部组织安全审计 |
| 告警规则定义 | issues-and-alerts | 平台 PostgreSQL 权威保存版本化规则 | 组合校验原子；规则定义与实例快照分离 |
| 告警评估、实例和指标证据 | 数据处理与存储系统 | 公开 Query；规则变更经 Outbox/BullMQ 传播 | 数据不足/暂停不等于恢复；实例保留触发时规则快照 |
| 通知与已读状态 | issues-and-alerts | 平台 PostgreSQL；生成任务经 Outbox/BullMQ | 同一业务动作对同一成员去重；已读不等于业务已处理 |
| 资源策略 | usage-and-policy | 平台 PostgreSQL 保存配置与版本；接入/处理系统保存应用投影 | 平台默认/组织完整覆盖/项目上限覆盖边界固定；保存与传播分离 |
| 资源用量 | 数据接入、处理与存储系统 | 公开只读用量投影 | 组织周期与时区一致；返回水位、降级、采样和完整性 |
| 组织安全审计 | audit | 平台 PostgreSQL | 只记录 PRD 规定的高风险动作；摘要最小披露且不可由普通用户修改 |
| 幂等、Operation Result、Outbox 与任务结果 | operations | PostgreSQL 权威；BullMQ 负责执行调度 | 同键同请求返回同结果；不同请求摘要冲突；队列状态不替代业务状态 |

跨领域用例由应用层显式编排。项目创建、邀请接受、所有权转让、令牌创建和生命周期变更必须在单一 PostgreSQL 事务中维护可本地保证的不变量；跨系统动作通过 Outbox 和状态投影实现，不使用分布式事务。

## 5. 公开 API 总体契约

### 5.1 协议与版本

- 浏览器公开 API 使用 HTTPS REST/JSON，并置于显式主版本命名空间；同一主版本内只允许向后兼容扩展；
- 每个操作具有稳定 `operationId`，Zod 4 系列 Schema 是管理契约来源，生成/校验 JSON Schema 与 OpenAPI；
- 外部输入先按 `unknown` 运行时校验，再进入应用用例；数据库行和下游响应同样不得因 TypeScript 类型而被无条件信任；
- 普通 Query 使用 GET；资源创建使用 POST；版本化局部修改使用 PATCH；归档、恢复、转让、撤销、接受邀请等业务动作使用显式 Command，不使用含义模糊的字段切换；
- Source Map 二进制不通过通用 JSON API 中转；公开 API 创建短期上传/下载意图并完成确认；
- 机器可读 OpenAPI 尚未生成，本文操作清单是正式契约的设计输入，不代表仓库已有端点。

### 5.2 Query 响应

Query 使用统一语义结构：

- `data`：当前用户有权查看的资源或列表；
- `meta`：请求标识、读取时点，以及按业务需要返回的对象版本、组织时区、分页、总量、计算水位、完整性、采样和降级说明；
- `allowedActions`：仅用于帮助 UI 呈现当前可能操作，不构成 Command 授权；
- 组合页面按分区返回独立状态和元数据，允许主数据成功而次要指标 `partial` / `stale` / `unavailable`；
- 权威查询成功但集合确实无记录时才是 `empty`；未知、超时、被采样掉或部分失败不能伪装为空集合或数值 `0`。

列表默认要求稳定排序和确定性次级键。时间线、高变动数据优先使用不透明游标；小型治理列表可使用页码。前端把当前分页表示写入 URL，但不能从已加载页面推断全量总数。

### 5.3 Command 响应、幂等与并发

- 所有非天然幂等 Command 使用 `Idempotency-Key`；作用域至少包含当前主体、操作类型和目标，服务端保存规范化请求摘要；
- 同键同摘要返回第一次结果；同键不同摘要返回稳定冲突，不执行第二次业务动作；
- 可并发修改资源携带权威版本或 ETag，并使用条件写入；冲突返回安全的当前版本与重新确认要求，不自动合并危险操作；
- 本地事务已完成的同步 Command 返回确定资源/结果；仍需后台动作时返回业务状态和 Operation 标识，但不把“邮件已排队”写成“邮件已送达”；
- 真正长操作返回 accepted/processing，并通过 Operation Result 或权威资源 Query 恢复；网络超时后不得换新幂等键盲目重试；
- Operation Result 至少区分 processing、succeeded、failed、expired/unavailable，并保留安全错误类别；内部 Worker/BullMQ 状态不直接暴露；
- 创建秘密的成功响应禁止缓存，明文只出现一次；Operation Result 和后续 Query 永不重新显示秘密。

### 5.4 错误模型

错误遵守 RFC 9457，并提供稳定机器错误码、请求标识和安全可显示信息。按需要附带字段错误、允许重试时间、当前版本、Operation 标识或安全目标；不得返回堆栈、SQL、内部队列名、对象存储键、令牌或账号枚举信息。

| HTTP/契约语义 | 用途 |
|---|---|
| 400 | 请求结构、路径或查询无法解析 |
| 401 | Session 缺失、过期或已撤销；不得泄露具体失效原因 |
| 403 | 已认证主体明确无权且披露资源存在不会扩大信息泄露 |
| 404 | 资源不存在，或需要通过不区分响应隐藏存在性 |
| 409 | 幂等键摘要冲突、唯一性、状态机或业务并发冲突 |
| 412 | 条件版本/ETag 不满足 |
| 422 | 结构合法但违反公开业务组合规则 |
| 429 | 限频；只在安全时返回允许重试时间 |
| 503 | Redis Session 或其他权威依赖不可用，且没有可安全返回的陈旧/部分投影；受保护写入失败关闭 |

写操作不会使用部分成功掩盖事务失败。批量只保留 PRD 已要求的接入事件逐项结果；管理平台第一版不新增通用批量 Command。

## 7. 权限、Session 与内部能力令牌

### 7.1 权限计算

- 第一版角色保持组织所有者、组织管理员、项目管理员和普通成员，不增加自定义角色或细粒度按钮权限系统；
- 组织所有者/管理员默认访问组织内项目；项目显式关系与组织继承分别保存，查询时计算有效权限并返回来源；
- `allowedActions` 是当前投影，所有 Command 仍重新读取当前成员关系、资源版本和生命周期；
- 项目进入回收站后不依赖删除前项目角色继续授权，只有组织所有者/管理员通过 B8 访问；
- D2 只接受正式平台管理员身份；该身份来源、授予/撤销和平台级审计仍是产品阻塞，不能由组织角色推导；
- 下游处理系统不自行解释浏览器角色；只消费 platform-api 基于当前授权签发的最小能力，并继续检查资源边界。

### 7.2 Redis Session 安全

- 使用专用 Session Redis 角色/命名空间，禁止会话键受到普通缓存淘汰策略影响；生产需与 BullMQ/缓存形成容量与故障隔离；
- Cookie 只保存随机 Session ID，服务器以不可逆摘要索引；Cookie 使用主机限定、Secure、HttpOnly 和适合邀请/邮件顶层导航的 SameSite 策略；
- 登录后轮换 Session ID，退出立即撤销当前 Session；密码重置按已批准规则撤销全部 Session；A5 注销申请受理后同样立即撤销全部 Session，冷静期内禁止正常登录；其他账号状态变化的 Session 影响仍由正式产品契约返回；
- 空闲期限和绝对期限同时存在，精确数值留给安全/部署专题；客户端活动不能无限延长绝对期限；
- Redis 不可用时受保护 API 失败关闭，并产生去敏安全指标；不得使用前端缓存权限继续写入；
- Session 内容不保存密码、私密令牌、客户端密钥明文、完整邀请/重置令牌或长期下游能力令牌。

### 7.3 CSRF 与公开认证端点

- 有状态 Session 使用同步 CSRF 令牌；SPA 从安全 Session Query 获取并在 POST/PATCH/DELETE 等非安全方法自定义 Header 中提交；
- 同时验证 Origin/目标 Origin 和适用 Fetch Metadata；Cookie 凭据 CORS 只允许显式受控来源，禁止通配符；
- GET/HEAD/OPTIONS 不改变业务状态，邮箱验证和密码重置链接只建立短期意图，最终消费由受 CSRF 保护的 POST 完成；
- 注册、登录、重置、验证和邀请端点使用多维限频与防枚举响应；Redis 可执行限频计数，但权威账号状态仍在 PostgreSQL；
- 验证、重置和邀请原始令牌只在客户端短暂交换，服务端保存摘要，日志和 Referrer 不得包含原始值。

### 7.4 内部能力令牌

- 能力令牌仅由获授权的内部签发方产生，采用短期、不可刷新、可轮换签名的结构；具体算法和密钥托管进入安全/部署评审；
- 声明至少限定签发方、受众、主体、资源、动作、签发/到期时点、安全版本和唯一标识；不放入无关 PII；
- 工作负载身份与能力令牌双重校验；只有令牌而无可信服务身份，或只有服务身份而无资源动作范围，都不能执行用户范围数据访问；
- 跨服务重试复用同一业务操作/幂等上下文，不通过签发新令牌造成重复副作用；
- 高风险内部 Command 继续写入其所属业务审计，能力令牌验证日志只保留摘要和关联标识。

## 8. 事务、并发与关键业务不变量

| 场景 | 事务/并发要求 | 失败恢复 |
|---|---|---|
| 注册 | 账号与个人工作空间原子创建；邮箱唯一约束；验证邮件 Outbox 同事务 | 邮件失败不回滚账号；重发遵守冷却并去重 |
| 邀请接受 | 邀请状态、邮箱匹配、成员关系和审计原子 | 重复接受返回现有结果；角色/过期冲突返回最新摘要 |
| 所有权转让 | 锁定组织和相关成员；事务结束后恰有一个所有者 | 冲突不产生双所有者或无所有者 |
| 项目创建 | 项目、默认环境、默认客户端密钥、安全策略元数据和审计原子 | 任一步失败整体回滚；重试返回原项目 |
| 私密令牌创建 | 元数据、摘要和审计原子；明文仅成功响应生成 | 超时先查 Operation Result；不得重新显示或重建原明文 |
| 问题/告警修改 | 使用所属服务权威版本；platform-api 不做本地乐观授权 | 下游超时查询 Operation/权威对象，不重复副作用 |
| Source Map 替换 | 元数据版本、摘要幂等、对象引用和处理任务一致 | 上传对象未确认前不替换当前有效文件；失败保留旧文件 |
| 项目设置/环境 | 两类对象各自版本；同标签内原子保存 | 冲突返回当前值，不跨标签“全部保存” |
| 项目生命周期 | 归档、恢复、回收站、deleting 使用单一状态机版本 | 冲突清除旧危险确认；删除任务可续跑且幂等 |
| 通知已读 | 按通知和账号幂等更新，同时返回权威未读版本 | 超时重新查询通知与计数，不本地减一当权威 |
| 资源策略 | 配置版本与 Outbox 原子；传播结果异步 | 保存成功与应用完成分离，失败保留旧生效投影或明确未知 |

数据库默认使用满足用例的最小隔离级别，并依靠唯一约束、条件更新、行锁和确定锁顺序维护不变量；只有确有写偏差风险的用例提升隔离或显式锁定。序列化失败、死锁和瞬时连接错误只在应用层证明安全且有界时重试。

## 9. Outbox、BullMQ、缓存与对象存储

### 9.1 Outbox 与 BullMQ

- Outbox 与领域写入同一事务提交，负载只保存最小引用、任务类型、业务幂等键、目标和安全版本，不复制密码、令牌或大对象；
- Relay 使用租约领取、发布和确认；崩溃发生在发布前则重试，发生在发布后确认前可能重复投递，因此消费者必须幂等；
- BullMQ 负责延迟、优先级、重试和执行租约；永久错误不重试，瞬时错误使用有上限退避和抖动；
- 任务最终失败写入 PostgreSQL 权威失败记录，保留安全原因、尝试次数、最后时间和处置状态；不能只依赖 Redis 中可能清理的失败 Job；
- 邮件、通知、策略传播、Source Map 后续任务和删除编排分别使用有界队列/并发，不允许一个任务类型耗尽所有 Worker；
- 重放需要明确任务类型、范围、权限和审计，不建设面向普通用户的通用任务中心。

### 9.2 Redis 缓存

- 缓存只用于可重建读取投影；第一版优先不缓存，只有测量证明收益且定义权威版本、作用域、TTL 和失效事件后才启用；
- 权限、角色、允许操作、Session 以外的安全状态、秘密、令牌明文、删除状态和 Operation Result 不得仅由普通缓存回答；
- 缓存键必须包含组织/项目/账号作用域和公开查询版本，禁止跨租户碰撞；
- Command 提交后通过 Outbox 失效相关键，TTL 是失效失败的兜底，不是正确性唯一机制；
- 缓存不可用时回源权威服务或返回明确不可用，不能把缓存空值当成业务空值。

### 9.3 S3 兼容对象存储

- Bucket/前缀保持私有，客户端不能构造永久 URL；对象键使用不可猜测内部标识，不直接拼接原始上传路径；
- 创建上传意图前校验项目、发布、文件路径、大小、类型、替换权限和资源策略；上传意图短期、单对象、单动作；
- 上传完成后服务端验证对象存在、大小和摘要，再以数据库事务激活元数据并创建后续处理任务；仅上传成功不等于 Source Map 可用；
- 同摘要重复上传幂等返回现有文件；不同摘要替换保持旧文件有效，直到新对象验证与元数据切换成功；
- 下载每次重新鉴权并生成短期意图；客户端上报密钥永远不能读取 Source Map；
- 项目永久删除通过幂等清理任务删除对象和元数据，失败可重试并阻止错误宣称永久删除完成；
- 供应商、区域、服务端加密、版本控制和备份策略进入测试/部署/发布专题。

## 10. 跨系统组合与一致性

- 浏览器只调用 platform-api；platform-api 对处理/存储系统使用公开 Query/Command 和 BACKEND-003 能力令牌；
- 平台数据库不复制原始事件、问题完整样本或时序指标作为第二权威；必要短期缓存必须保留来源、水位和陈旧语义；
- 页面组合 Query 为各依赖设置有界超时和独立结果分区。身份/项目权威失败时整体失败；次要指标失败时返回 partial/unavailable 分区；
- 跨系统 Command 不使用分布式事务。平台先提交本地配置与 Outbox，再由 Worker 传播；公开状态区分 saved、propagating、applied、failed/unavailable；
- 下游 Command 接受业务幂等键和预期资源版本；重复能力令牌或重复 BullMQ 投递不能重复计数、通知或删除；
- 服务间错误统一映射为公开稳定错误，不透传下游堆栈、主机名或内部错误码；
- C7 诊断只展示经服务端整理的阶段事实和最近安全证据，不提供逐事件内部轨迹或原始队列日志。

## 11. 数据展示口径

| 页面/数据 | 权威来源与计算口径 | 更新时间/水位 | 采样、降级和空值 |
|---|---|---|---|
| B5 资源用量 | 接入/处理系统的同组织、同周期、同策略计数；周期按当前组织业务时区 | 返回读取时点、周期边界、计数水位和策略版本 | 降级/采样必须解释；未知或部分不显示 0 |
| C2 项目概览 | 服务端权威健康状态＋同一 URL 筛选下问题、影响用户估算、活动告警和最近数据 | 各分区独立更新时间，整体标明最旧依赖 | 影响用户是估算；任一分区部分失败不伪造健康评分 |
| C3 问题列表 | 处理系统按规范化筛选、排序和分页查询问题聚合 | 返回查询水位、排序稳定键和可用总量 | 样本不用于推导问题总量；总量未知则省略/标未知 |
| C4 问题详情 | 问题聚合权威对象＋有限代表样本＋问题级活动 | 问题版本与样本/活动各自水位 | 样本不是完整事件历史；缺样本不等于无发生 |
| C5 接口指标 | 处理系统规范化接口维度的失败率、耗时和慢请求聚合 | 时间范围、分辨率、计算完成水位 | 返回分母、采样、降级、完整性；无分母为不可计算而非 0% |
| C6 页面指标 | 处理系统安全页面维度的 LCP/INP/CLS/加载耗时聚合 | 同 C5，并返回指标适用性 | 指标不可用与无问题分开；不计算全项目性能评分 |
| C7 接收诊断 | 接入/处理系统当前阶段状态、原因和有限最近证据 | 当前状态版本及各阶段最后确认时间 | 已接收只表示可靠缓冲；拒绝样本不能自动转为 allowlist |
| C9 Source Map | 平台元数据＋对象验证＋处理系统重解析投影 | 文件版本、任务更新时间和处理水位 | 不展示未经契约支持的百分比；无匹配与处理中分开 |
| C10/C12 告警 | 平台规则版本＋处理系统评估/实例/快照 | 评估时间、指标水位和状态轨迹版本 | 数据不足/暂停不等于恢复；采样影响随证据返回 |
| D1 通知 | PostgreSQL 当前账号可见通知和未读计数 | 服务端排序时点、计数版本和完整性 | 权限变化/保留会改变计数；列表页数不用于计算未读总数 |
| D2 资源策略 | PostgreSQL 配置值/来源＋各接入/处理节点应用投影 | 保存版本、传播更新时间和生效时间 | 配置不受事件采样影响；传播未知不能显示已应用 |

所有时间点使用 UTC 存储；日历周期和展示按当前组织 IANA 业务时区解释。历史真实时间点不变，时区修改不重写事件。数值格式化只在前端完成，不改变后端口径。

## 12. 页面状态与服务端语义映射

| 前端状态 | 服务端语义 |
|---|---|
| loading | 尚未取得结果，仅是客户端请求状态，不由缓存旧值伪装 |
| empty | 权威 Query 成功、权限有效、查询范围明确且确实无记录 |
| error | 请求失败且无可安全使用的数据；使用 RFC 9457 稳定错误 |
| forbidden | 已认证但无权限，且披露目标存在安全；否则使用不区分 404 |
| processing | Command/Operation 已受理且业务结果尚未完成 |
| partial | 组合 Query 至少一个分区成功且至少一个分区失败/不完整；逐分区携带原因 |
| stale | 返回最近成功投影并明确权威更新时间、陈旧原因和刷新状态 |
| unavailable | 权威依赖当前不可用且没有安全陈旧投影；不得显示空值或 0 |
| conflict | 幂等摘要、对象版本、唯一约束或状态机冲突；返回安全当前状态和恢复动作 |
| archived/trash/deleting/deleted | 来自项目权威生命周期；权限和允许操作随状态变化，不由路由或缓存推断 |
| propagating | 配置已保存但尚未被全部目标应用；与 processing 任务内部状态分离 |

## 13. 审计、隐私、保留与删除

- B7 只向组织所有者/管理员提供 PRD 指定高风险安全审计；认证安全日志、平台级审计和问题活动分别存储，不混成一个权限模型；
- 审计记录保存主体摘要、动作、目标、结果、时间、请求/Operation 关联和必要安全变化，不保存密码、Cookie、令牌明文、Source Map 内容或事件敏感字段；
- 普通问题状态、负责人和备注进入问题活动；只有 PRD 指定的高风险动作进入组织安全审计；
- 私密令牌、验证/重置令牌、Session ID 和上传意图只保存安全摘要或短期服务器状态；一次性交付响应禁止缓存和通用日志；
- 项目归档立即停止接收与告警；回收站立即失效客户端密钥、撤销私密令牌并阻止普通访问；永久删除必须清理平台数据、处理数据、对象和成员关系后才完成；
- 删除使用可续跑的幂等编排与逐系统确认，不因部分成功宣称永久删除；只保留 PRD 允许的最小非监控安全审计摘要；
- PRD 已给出的保留期由后端策略执行；通知、Session、Operation Result、Outbox/死信和部分安全意图的精确保留仍在缺口表中，不由实现自行决定。

## 14. 可观测性与运维设计边界

后端专题确认必须具备以下信号，具体数值阈值、SLO、告警和部署拓扑留给测试/部署/发布专题：

- platform-api 请求率、延迟、错误类别、限频、DB/Redis/下游耗时和连接池状态；
- PostgreSQL 事务冲突、死锁、慢查询、Migration 状态、Outbox 待投递量和最老年龄；
- BullMQ 等待/延迟/活跃/失败量、重试次数、最老任务年龄和按任务类型的资源占用；
- Session Redis 可用性、延迟、内存、淘汰、持久化/复制状态和异常撤销失败；普通缓存与 Session 指标分离；
- 对象上传/验证/下载/删除结果、孤儿对象和摘要不一致；不记录签名 URL；
- 跨系统 Query/Command 的受众、结果类别、超时和水位延迟，不记录能力令牌；
- 业务不变量指标：重复项目/通知/任务、无所有者组织、删除停滞、策略传播停滞和审计写入失败。

日志采用结构化关联标识，但请求标识、业务操作标识、幂等键摘要和追踪标识用途分离。高基数字段、完整 URL 查询、邮箱、用户上下文和秘密不进入通用指标标签或日志。

## 16. ADR 判断与明确延后

至少需要在实施前形成并 accepted 的长期决策：

1. 管理平台后端主运行时、模块化单体/Worker、Fastify、PostgreSQL/Kysely 和 Zod/OpenAPI 技术基线；
2. Transactional Outbox、Redis/BullMQ、Session 权威存储和私有 S3 兼容对象存储的基础设施与可靠性边界；
3. 不透明 Cookie Session、CSRF 和内部短期能力令牌的安全架构。

可以拆分为多份 ADR 以便安全、数据库和基础设施领域分别评审；本文不预分配 ADR 编号，也不修改 ADR-001 至 ADR-006 的 `proposed / not-started` 状态。accepted 只授权决策，不代表 implemented。

已批准测试/部署/发布设计为 AWS 服务族、CI/发布模型、浏览器矩阵、性能/SLO、备份恢复和 Runbook 建立方向。精确依赖/引擎版本、主区域、实例/配额、连接池、任务并发/重试、Session/密码安全参数、缓存/对象生命周期和真实容量基准仍未锁定。它们不能缺省实施，必须在进入对应 planning/实现或发布前完成相应 ADR、规格和验证门禁。

## 17. 已否决与重新评估条件

| 方案 | 当前否决原因 | 重新评估条件 |
|---|---|---|
| Go 或 Kotlin/Spring Boot 主栈 | 双语言契约和工程成本高，当前无性能/合规证据抵消 Node.js 方案收益 | 性能、团队、合规或运行隔离证据变化 |
| 第一版按领域拆微服务 | 提前引入网络故障、分布式事务、部署和可观测性复杂度 | 出现独立扩缩容、隔离、团队所有权或发布瓶颈 |
| 浏览器 BFF、SSR 或直接调用多个服务 | 与已批准 SPA→platform-api 单一公开边界冲突 | 产品新增经批准的 SSR/独立客户端需求 |
| PostgreSQL-only 任务队列 | 用户选择 BullMQ 的延迟、重试和调度能力；仍保留 Outbox 保证原子性 | Redis/BullMQ 成本长期超过收益且 PostgreSQL 足以稳定承担 |
| 无 Outbox 直接向 Redis 投递 | 数据库事务和任务投递存在不可恢复双写窗口 | 不重新评估；除非使用另一种有正式原子性证明的机制 |
| 第一版独立 OpenSearch/Elasticsearch | 无搜索规模证据，却增加索引一致性、删除传播和运维系统 | 索引/分区无法满足经测量查询目标且具备完整治理方案 |
| PostgreSQL 权威 Session | 恢复路径清晰但用户选择 Redis 权威 Session 获得 TTL 与共享访问能力 | Redis 认证关键基础设施无法达到可靠性/成本目标 |
| 浏览器 JWT/Bearer Token | 撤销、权限变化和浏览器暴露面更复杂，与已确认不透明 HttpOnly Session 冲突 | 新客户端形态和安全 ADR 明确改变认证边界 |
| 内部调用转发浏览器 Cookie | 扩大 Cookie 受众和下游权限，形成混淆代理风险 | 不重新评估；必须使用服务身份和最小内部授权 |
| 每次内部调用在线回查中央授权 | 增加级联故障和往返，用户选择短期能力令牌 | 能力令牌治理无法满足即时撤销要求且有高可用授权服务方案 |
