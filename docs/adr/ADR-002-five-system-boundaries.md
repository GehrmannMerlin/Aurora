# ADR-002：划分五大系统边界

- 日期：2026-07-27

## 背景

Aurora 从浏览器捕获事件，到服务端接收、异步处理、查询和管理平台展示，存在不同运行环境、可靠性要求和安全边界。如果按页面、部署单元或开发人员随意组织，容易出现 SDK 承担服务端逻辑、管理平台直连数据库或协议定义分散。

## 决策驱动因素

- SDK 不能影响宿主页面；
- 接入路径需要快速、可靠和可限流；
- Source Map、聚合和告警属于耗时异步处理；
- 管理平台必须通过稳定 API 使用数据；
- 公共事件协议必须跨端一致；
- 第一版允许同一应用部署多个逻辑模块，但代码边界不能合并。

## 候选方案

### 方案 A：五大职责系统

划分 SDK、数据接入、数据处理与存储、管理平台、公共协议五个一级系统。

优点：

- 每个系统有清晰输入、输出和非职责；
- 运行环境和可靠性要求自然分离；
- 公共协议拥有独立权威位置；
- 允许早期合并部署而保持代码边界；
- 便于针对系统风险设计测试和监控。

缺点：

- 需要维护接口和依赖规则；
- 数据接入与处理之间需要可靠缓冲；
- 小规模阶段看起来比单体目录更复杂；
- 跨系统功能需要明确归属。

### 方案 B：按可部署应用划分

只划分浏览器 SDK、服务端应用和管理平台，接入、处理、协议都放入服务端。

优点：

- 初始目录和部署简单；
- 服务端内部调用直接；
- 少量开发者容易快速开始。

缺点：

- 接入与耗时处理容易耦合；
- 协议可能成为服务端私有定义；
- 管理平台可能依赖数据库模型；
- 服务端单体随着聚合、告警、Source Map 增长而职责失控。

### 方案 C：从第一天拆成微服务

接入、队列消费者、Source Map、聚合、查询、告警和权限分别独立部署。

优点：

- 运行和扩容边界清晰；
- 故障和资源可以隔离；
- 适合高事件量和大团队。

缺点：

- 第一版运维、网络和数据一致性复杂度过高；
- 需要服务发现、追踪、部署和故障治理；
- 很多容量假设尚无真实数据；
- 影响核心产品闭环交付速度。

## 最终决策

提议选择方案 A：五大职责系统。

本节在 ADR accepted 前只是建议。五大系统是逻辑和代码边界，不要求第一版立即拆成五个独立部署单元。

## 结果与影响

### 正面影响

- SDK、接入、处理和平台职责清楚；
- 耗时处理不会阻塞上报请求；
- 协议和运行时校验可复用；
- 管理平台不会扩散存储内部结构；
- 后续可以按真实规模拆分部署。

### 负面影响与代价

- 需要定义跨系统接口和失败语义；
- 早期同部署时仍要维护逻辑隔离；
- 事件状态和可观测性需要跨阶段设计；
- 开发者必须理解系统归属而不能随意放置代码。

### 未解决问题

- 各系统的具体部署拓扑；
- 队列和数据库技术；
- 查询服务是否独立部署；
- 组织和权限模块的物理位置。

## 实施约束

- SDK 只采集、处理并上报标准事件；
- 接入只做鉴权、限制、校验、过滤和可靠接收；
- 数据处理负责清洗、分组、Source Map、聚合、存储和告警；
- 管理平台只通过公开 API；
- 公共协议不依赖业务系统；
- 同部署不允许跨越公开接口直接访问其他系统内部实现；
- 每个模块 README 声明职责、非职责、输入、输出和依赖。

## 迁移方案

ADR accepted 后，在 Monorepo 中为五大系统建立明确模块或目录。第一版可以让接入、处理和查询在同一服务端应用部署，但使用模块接口、队列或任务边界隔离。随着事件量和团队规模增长，再通过新 ADR 评估物理拆分。

## 回滚方案

如果评审认为五大边界不适用，可在正式代码形成前撤回本提案。实施后改变一级系统必须创建新 ADR、列出数据和接口迁移，并保留旧边界文档。

## 验证方式

- 每个模块 README 有职责和非职责；
- 管理平台无数据库和内部队列依赖；
- SDK 无服务端分析和 Source Map 逻辑；
- 接入请求不执行复杂聚合；
- event-schema 无业务模块依赖；
- 架构检查阻止跨边界私有引用。

## 重新评估条件

- 事件量要求独立扩缩容；
- 某系统的职责持续变化或无法独立测试；
- 部署或组织结构发生重大变化；
- 五大边界造成明显重复或不必要网络调用；
- 新业务超出前端监控范围。
