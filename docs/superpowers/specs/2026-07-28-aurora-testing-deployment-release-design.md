# Aurora 第一版测试、部署与发布设计

## 1. 文档定位与当前效力

本文收口 Aurora 第一版的测试分层、CI、兼容与性能承诺、环境、部署拓扑、数据库迁移、备份恢复、制品、发布、回滚、可观测性和 Runbook。用户已于 2026-07-29 批准三个关键选择及第 4—18 节从 approved PRD、长期规范和已批准前序专题推导出的完整方案；当前进入正式化、required ADR 与实施就绪审查。

本文 `status: approved` 只表示设计内容已批准，可作为正式化和 ADR 评审输入；不表示代码、CI、AWS 账号/资源、数据库、秘密、制品、部署或 npm 发布配置已经存在，也不授权创建它们。此次批准不修改任何 ADR 状态；required ADR 仍须独立评审并达到 `accepted`，且最终实施就绪审查须获用户明确批准，相关内容才能进入 `writing-plans`。

## 2. 权威输入、范围与状态解释

- approved PRD 决定第一版业务范围，特别是 SDK 不影响宿主、可靠接收、异步处理、数据保留、删除、发布/部署和 Source Map 语义；
- approved 架构规范决定五大系统边界、单向依赖、管理平台只使用公开 API、可靠接收与异步处理边界；
- approved 测试规范决定风险优先分层、共享契约样本、真实浏览器验证、覆盖率基线和分级 CI 阻断；
- 已批准前四专题基线、管理平台 UX/UI、前端技术栈和管理平台后端设计决定需要验证的组件、公开边界和失败模式；
- ADR-001 至 ADR-006 仍为 `proposed / not-started`。本文引用它们只为整理正式化材料，不把候选方案写成实施授权；
- 仓库当前没有代码、机器 OpenAPI、事件协议、模块 README、CI、AWS 资源、部署清单、发布脚本或运维实现。本文所有服务、指标和流程均为设计，不是现存能力。

第一版不设计多云主动—主动、跨区域双活、私有化交付、Kubernetes 平台、通用 GitOps/内部开发者平台、完整审批系统、24×7 企业值班产品或自动收费扩容。将来只有在产品、合规、规模或团队证据改变时才重新评估。

## 3. 已确认关键决策

### 3.1 TD-001：部署运行模型

用户选择方案 A：采用 AWS 单一主云的托管容器与托管数据服务模型。

| 责任 | 已确认方向 |
|---|---|
| 管理平台前端 | Vue SPA 构建为静态资源，由私有 S3 源站配合 CloudFront 分发 |
| 管理平台应用 | `platform-api` 与 `platform-worker` 分别运行在 ECS/Fargate，Worker 无公网入口并独立扩缩容 |
| 平台 PostgreSQL | Amazon RDS for PostgreSQL；生产采用 Multi-AZ，版本和容量后续锁定 |
| Redis | Amazon ElastiCache；Session、BullMQ 和普通缓存在凭据、容量、淘汰、监控和故障边界上隔离 |
| 私密对象 | Source Map 等对象使用私有 S3，实施短期单对象意图、加密、版本和删除传播 |
| 网络与治理 | 公开流量只进入 CDN/负载均衡与公开 API；环境和资源使用版本化 IaC |

该选择不意味着数据接入、可靠缓冲、异步处理和监控存储的物理技术已经决定。它们仍只有业务与高层架构基线，必须在相应实施规格和 ADR 中完成 AWS 落位，不能把 BullMQ 或管理平台 PostgreSQL 误用为监控事件主缓冲/主存储。

### 3.2 TD-002：发布、迁移与回滚模型

用户选择方案 A：不可变制品、分阶段晋级、数据库 expand/contract 兼容迁移和受控生产批准。

| 责任 | 已确认方向 |
|---|---|
| CI/CD | 使用 GitHub Actions；同一提交生成不可变制品，先部署预发布环境，再由受保护生产 Environment 人工批准 |
| 云身份 | GitHub Actions 使用短期 OIDC 工作负载身份访问 AWS，不保存长期 AWS Access Key |
| API/Worker | ECR 镜像以内容摘要标识；ECS 滚动部署，启用健康检查、部署熔断和告警回滚条件 |
| SPA | 内容哈希静态资源使用长期不可变缓存；入口文档短缓存/不缓存；发布切换不覆盖旧资源 |
| 数据库 | 使用向后兼容的 expand → migrate/backfill → switch → contract；破坏性收缩不得与依赖旧结构的代码同批上线 |
| SDK 发布 | npm 发布与平台部署分离；使用 npm Trusted Publishing/来源证明；已公开坏版本通过弃用和补丁版本修复，不把 `unpublish` 当回滚机制 |
| 紧急修复 | 仍走同一受审流水线和不可变制品；只允许有事故记录的范围化门禁，事后补齐完整验证 |

### 3.3 TD-003：质量、兼容性与可靠性承诺

用户选择方案 A：平衡型生产基线，把快速 PR 阻断、夜间扩展验证和发布级完整证据分层。

| 维度 | 已确认方向 |
|---|---|
| PR | 类型/静态/架构检查、受影响单元与集成测试、共享契约、覆盖率、构建/导出、核心 Chromium 与关键 Playwright 回归 |
| main/nightly | Chromium/Firefox/WebKit、完整 E2E、示例、稳定性/内存、安全和较重的集成验证 |
| release | 完整支持矩阵、性能/负载/积压、迁移/恢复演练证据、制品/SBOM/来源证明和发布检查 |
| 浏览器承诺 | Chrome、Edge、Firefox 最近两个稳定主版本；Safari 与 iOS Safari 最近两个主版本；Android Chrome 当前与前一稳定主版本；不支持 IE |
| 可用性 | 公共数据接入入口与管理平台公开 API 分别以月度 99.9% 为第一版目标 |
| 平台数据恢复 | 单区域多可用区运行故障目标：PostgreSQL `RPO ≤ 5 分钟`、`RTO ≤ 60 分钟`；区域级灾难另行定义较低第一版目标 |
| 处理及时性 | 已可靠接收事件的持久性和可查询新鲜度分别衡量，不能用 HTTP 接收成功替代处理完成 |

三个关键选择和以下完整派生方案均已批准；不再增加用户级工具、命令或配置问题。文中未决项、阻塞项和重新评估条件保持有效。

## 4. 环境、账号与网络拓扑

### 4.1 环境分层

| 环境 | 用途 | 数据与访问 | 发布方式 |
|---|---|---|---|
| 本地开发 | 快速反馈、单元/组件/契约和局部集成 | 只使用合成数据与本地/隔离测试依赖；不得复制生产数据 | 开发命令，不产生可发布事实 |
| PR 临时环境 | 只在高风险 UI/API 变更需要人工验收时创建；不是每个 PR 的强制完整平台 | 短期、最小权限、自动过期；默认不接真实用户或真实监控数据 | 由 PR 流水线按需创建/销毁，具体实现留给 planning |
| 共享预发布 | 与生产同类部署单元、Cookie/CSRF、迁移和可观测性验证；运行 E2E、恢复与发布候选检查 | 独立账号/网络/数据库/Redis/S3；只允许合成或经批准的脱敏测试数据 | main 候选自动部署，同一不可变制品晋级生产 |
| 生产 | 第一版真实业务 | 独立生产 AWS 账号、VPC、KMS、秘密和数据；最小人员权限 | 受保护生产 Environment 人工批准 |

至少采用“非生产账号＋生产账号”隔离；共享管理账号、日志/备份账号是否单独建立由 AWS 组织治理 ADR 决定。任何环境都不得共享生产数据库、Session Redis、BullMQ、对象 Bucket 或加密密钥。

### 4.2 第一版区域与可用区

- 第一版采用单主区域、生产多可用区，不承诺跨区域主动流量；
- 主区域必须由目标用户地域、数据驻留、邮件/对象/日志合规、延迟和服务可用性共同决定；当前仓库没有这些产品/合规输入，`TDR-GAP-01` 阻塞实际区域选择；
- 预发布尽量与生产同区域和同类服务，以暴露配额、网络和托管服务差异；
- 区域级灾难恢复依靠跨区域备份副本和重建 Runbook，不宣称自动故障转移。

### 4.3 管理平台入口

推荐使用一个管理平台公共主机：CloudFront 同时承载私有 S3 静态源，并将 `/api/*` 动态转发到只接受受控入口的 ALB/`platform-api`；API 响应不得由 CDN 缓存。这样可以保持主机限定 Session Cookie、CSRF 和 SPA 路由边界清晰。SDK 数据接入使用独立公开主机和客户端上报密钥认证，不共享浏览器 Session。

- CloudFront 对静态资源启用安全头和正确缓存；历史路由回退只能对 SPA 页面生效，不能把 API 404 改写为 `index.html`；
- ALB 只路由到私有子网中的 `platform-api` ECS Service；Worker、RDS、ElastiCache 和私密 S3 无公网入口；
- API 与 Worker 使用不同任务角色、安全组、扩缩容和健康信号；
- 出站访问使用显式允许和 VPC Endpoint/受控 NAT；对象、数据库和 Redis 访问遵循最小网络路径；
- 公共入口的 DDoS/WAF、速率限制、CSP/HSTS、TLS 和安全头参数需在安全评审中锁定，不能由框架默认值决定。

## 5. 基础设施、配置、秘密与供应链

### 5.1 IaC 与变更治理

派生方案推荐使用 AWS CDK（TypeScript）管理账号内基础设施，原因是已批准前后端主语言为 TypeScript，且 CDK 可以形成可审查的 CloudFormation 变更。该选择属于长期工具决策，需纳入部署 ADR；在 ADR accepted 前不得创建工程。

- 基础设施按环境形成独立 Stack/Stage，生产变更显示计划差异并经过审批；
- 控制台手工修改不是常规路径；事故期临时修改必须留审计、Owner、到期和回填 IaC 任务；
- 资源命名、标签至少包括系统、环境、Owner、数据分类和成本归属；
- 云服务、数据库和运行时版本不得使用浮动 `latest`，升级先在预发布验证并记录兼容/回滚条件；
- 生产删除保护、保留策略和高风险 IAM 变化需要单独审批。

### 5.2 配置与秘密

- 非秘密配置由版本化部署配置或 SSM Parameter Store 管理；秘密、签名材料、Pepper、外部服务凭据由 Secrets Manager 与 KMS 管理；
- 应用只通过 ECS Task Role 读取当前环境所需秘密，不把秘密写入镜像、仓库、构建日志、环境导出或前端资源；
- GitHub Actions 通过 OIDC 交换短期 AWS 凭据，并按环境/工作流限制角色；生产角色与非生产角色分离；
- 秘密建立轮换、双版本兼容、撤销和故障 Runbook；令牌/Session/签名算法和期限仍须安全 ADR；
- Source Map、测试 trace、截图、日志和故障包均按敏感资产处理，发布流水线必须执行秘密扫描与日志脱敏检查。

### 5.3 制品与可追溯性

每次可发布构建生成发布清单，至少关联 Git commit、构建工作流、前端静态资源摘要、API/Worker 镜像 digest、数据库 Migration 集合、公共契约版本、SDK 包版本、SBOM 和来源证明。

- API/Worker 镜像在 ECR 中以 digest 晋级，生产不从分支重新构建；
- SPA 资源以内容哈希和版本前缀保存，旧资源在兼容窗口内保留；
- SDK npm 包使用 SemVer、精确文件清单、打包后导出/体积/安装验证和来源证明；
- 公共协议、SDK、接入和消费者的兼容组合必须可从发布清单追溯；
- 制品签名/证明验证失败、SBOM 缺失、来源不明或镜像扫描存在未豁免高危问题时阻止发布。

## 6. 测试分层与模块质量策略

### 6.1 共用原则

- 测试按宿主影响、数据正确性、权限/秘密、不可逆生命周期、协议兼容和发布风险排序；
- 测试数据默认合成，不把真实生产事件、Cookie、令牌、邮箱、Source Map 或用户上下文放入 fixture、截图、trace 和日志；
- 外部输入均覆盖合法、非法、边界、超限、未知版本和恶意负载；
- 幂等、并发、超时、重试、部分失败、陈旧、不可用和恢复路径必须与成功路径同等可验证；
- 测试规范的覆盖率基线保持不变：Core 行覆盖率不低于 85%、分支不低于 80%；其他模块行不低于 70%、分支不低于 60%。覆盖率只是最低线，不能替代关键风险测试。

### 6.2 Monorepo 与公共协议

- 架构检查验证公开 exports、声明依赖、循环/反向/私有路径和环境边界；
- `event-schema` 的合法、非法、边界和旧版本样本由 SDK、接入、处理共同消费；
- 协议文档、Schema、生成类型和 OpenAPI 的差异阻止合并；
- 影响根配置、协议、公共类型或依赖矩阵的变更强制运行全部消费者，不得只按文件路径跳过。

### 6.3 SDK Core、Browser、插件与框架适配

- Core 单元/属性测试覆盖生命周期、重复初始化、采样、队列上限、批处理、重试上限、多实例和异常隔离；
- Browser 与插件在真实浏览器覆盖监听/代理安装、重复安装、释放、原生 API 恢复、递归采集保护、字段限制和隐私过滤；
- React/Vue 适配使用受支持框架版本验证安装、错误边界/钩子、卸载和不复制通用采集；
- 宿主安全场景覆盖无网络、慢网络、限流、页面卸载、插件抛错、多个 SDK 实例、被第三方修改的原生 API 和隐私禁止字段；
- 包级发布验证覆盖 ESM 导出、tree-shaking、副作用声明、类型、安装示例和打包体积。

### 6.4 数据接入与可靠缓冲

- 契约测试覆盖身份、密钥、来源、环境、大小、协议、Schema、隐私、采样、去重、限频以及批次逐事件结果；
- 故障注入验证“只有可靠写入后才确认接收”、进程终止后仍可处理、重复事件编号幂等和永久/暂时失败分类；
- 负载测试分别量化请求延迟、吞吐、限流、公平性、缓冲积压、水位和降级；
- 禁止用管理平台 BullMQ 或普通缓存代替事件可靠缓冲测试，直到该专题物理技术正式确定。

### 6.5 异步处理、聚合与存储

- 消费重放、重复投递、乱序、部分失败和进程终止不得重复问题计数、告警、通知或删除；
- 问题归并、再次出现、代表样本替换、分钟/小时/日聚合和 Source Map 严格匹配使用确定性样本；
- Source Map 覆盖同摘要幂等、显式替换、错误路径、边界资源、有限重解析和私密删除；
- 保留、回收站、永久删除和对象清理执行时间推进、跨存储确认与失败续跑测试；
- 性能/容量测试必须证明查询水位、采样、降级和空值语义在压力下仍准确。

### 6.6 管理平台前后端

- 前端使用 Vitest、Vue Testing Library、正式契约驱动的 MSW、Playwright、axe 和 Lighthouse；MSW 不替代真实服务契约/集成证据；
- platform-api 领域/应用层单元测试覆盖权限、事务、不变量、幂等摘要、版本冲突、RFC 9457 映射和敏感信息；
- PostgreSQL/Redis/BullMQ/S3 集成测试使用真实兼容服务验证事务、Outbox、Session 失败关闭、对象确认和删除，不以全量 mock 证明可靠性；
- A1—D2 关键链路覆盖认证、邀请、项目创建、接入、问题处理、告警、Source Map、危险生命周期、通知和策略传播；
- E2E 按适用页面验证 `loading`、`empty`、`error`、`forbidden`、`processing`、`partial`、`stale`、`unavailable`、冲突和生命周期状态。

## 7. CI 阶段、阻断与例外

### 7.1 Pull Request 必需检查

1. 文档元数据、内部链接、格式和 ADR 状态一致性；
2. 依赖/架构边界、秘密扫描、生成文件无漂移；
3. TypeScript、Vue 模板类型、Lint 和生产构建；
4. 受影响单元/组件/集成测试与覆盖率；
5. `event-schema`、公开 API 和跨系统契约测试；
6. SDK 构建、公共 exports、tree-shaking、包体积和核心 Chromium 宿主安全；
7. 管理平台关键 Playwright 回归、自动可访问性和代表页面性能烟雾检查；
8. 数据库 Migration 静态检查与向前/兼容路径测试；
9. IaC 合成、策略/安全扫描和计划差异（涉及基础设施时）。

“受影响范围”只能优化成本，不能削弱正确性：根配置、工作区锁文件、公共协议、API 契约、数据库 Migration、共享测试工具或依赖矩阵变化触发更广矩阵。每个必需检查失败都阻止合并。

### 7.2 main、nightly 与 release

| 阶段 | 附加证据 |
|---|---|
| main | 生成不可变候选制品、部署预发布、运行核心端到端和迁移烟雾；失败不晋级 |
| nightly | Firefox/WebKit、完整 E2E、正式示例、稳定性/内存、依赖/镜像安全、协议组合、队列/处理恢复和较长故障注入 |
| release | 完整浏览器/框架/运行时支持矩阵、性能/负载/积压、备份恢复、Migration/回滚、SBOM/来源证明、人工可访问性和发布检查表 |

### 7.3 Flaky 与豁免

- 不得重跑至偶然通过后忽略首个失败；重跑用于采集证据，不改变失败事实；
- 隔离 flaky 测试必须记录原因、风险、Owner、Issue 和最晚恢复日期；涉及权限、协议、数据丢失、删除、迁移或宿主破坏的测试不得隔离后发布；
- 安全漏洞、许可证、SLO 或性能预算豁免需要风险接受者、补救期限和发布记录；到期自动阻断；
- 紧急修复只能缩小非相关长时测试，不能跳过类型、契约、目标回归、制品完整性和生产审批；事故稳定后立即补跑完整发布证据。

## 8. 兼容性、可访问性与量化性能预算

### 8.1 浏览器支持矩阵

正式承诺以发布日可获得的稳定版本计算：

- 桌面：Chrome、Edge、Firefox 最近两个稳定主版本；Safari 最近两个主版本；
- 移动：iOS Safari 最近两个主版本；Android Chrome 当前与前一稳定主版本；
- 不支持 IE、非稳定预览版和已停止安全维护的系统浏览器；
- Playwright Chromium/Firefox/WebKit 用于自动回归，但 WebKit 不能单独证明真实 Safari/iOS；发布前必须有真实 Safari 与移动设备/可信设备云证据；
- 新浏览器主版本先进入 CI 矩阵，兼容后自然替换最旧版本；移除已承诺版本必须经过兼容/发布记录，必要时使用 ADR。

管理平台核心任务和 SDK 宿主安全使用同一产品矩阵；SDK 可在不受支持浏览器中安全不工作，但不得破坏宿主。框架适配的框架版本矩阵另由 SDK 公共兼容文档记录。

### 8.2 可访问性

- 管理平台以 WCAG 2.2 AA 为第一版目标；自动 axe 检查只能发现部分问题；
- 发布证据还包括键盘全流程、可见焦点、焦点恢复、200% 缩放、小屏、非颜色编码、动态状态宣告和代表流程屏幕阅读器检查；
- 高风险基线覆盖认证、表单错误、导航/作用域切换、表格/分页、标签页、弹窗、危险确认、一次性交付秘密和 C5/C6 图表文本摘要；
- 无障碍阻塞级缺陷不得以截图一致或自动扫描通过替代。

### 8.3 SDK 包体积预算

以下是第一版发布预算，统一以生产 ESM、最小化、gzip 后、排除 Source Map 的固定示例构建测量：

| 制品 | 预算 |
|---|---:|
| Core 基础包 | ≤ 10 KiB gzip |
| Browser＋Core 最小接入 | ≤ 30 KiB gzip |
| 单个可选采集插件增量 | ≤ 8 KiB gzip |
| 单个 React/Vue 框架适配增量 | ≤ 5 KiB gzip |

预算检查同时报告 raw、minified、gzip、依赖贡献和相对基线。超预算不是通过拆分重复依赖规避；若业务必需能力无法满足，必须提供测量证据、用户影响和兼容/迁移评审后调整。

### 8.4 SDK 运行开销预算

在版本化参考页面、设备档位、浏览器和事件脚本下测量：

- 初始化同步工作：桌面 p95 ≤ 20 ms，中档移动设备 p95 ≤ 50 ms；
- 参考场景中不得产生单次 SDK 归因的 >50 ms Long Task；
- 稳态附加 JS Heap 在稳定后 ≤ 5 MiB；
- 请求/错误捕获的同步包装开销 p95 ≤ 1 ms，不含异步网络发送；
- 队列、批量和重试必须严格遵守有界资源，长时断网测试中内存不能无界增长。

设备、浏览器、页面和采样脚本尚未建立，首次实现前必须形成可复现基准；达不到预算时不能通过关闭宿主安全或隐私限制换取性能。

### 8.5 管理平台性能预算

| 指标 | 第一版预算与口径 |
|---|---|
| 初始非图表路由 JavaScript | ≤ 300 KiB gzip；不包含只在 C5/C6 加载的 ECharts 路由块 |
| ECharts 及图表路由增量 | ≤ 250 KiB gzip，按需引入图表类型并懒加载 |
| Lighthouse CI | 代表性预发布移动配置 Performance ≥ 85；LCP ≤ 2.5 s、CLS ≤ 0.1、TBT ≤ 200 ms |
| 真实用户 INP | 获得足够有效样本后，核心页面 p75 ≤ 200 ms；样本不足显示 unavailable，不以实验室 TBT 冒充 INP |

认证、工作空间、问题列表、问题详情和 C5/C6 代表性页面分别测量；后端数据时间不隐藏在前端 LCP 分数中，API 延迟和页面渲染分开报告。预算以受控基准为发布门禁，真实用户指标以样本、水位和完整性解释。

## 9. 服务目标、容量与降级

### 9.1 可用性与延迟

- 数据接入公开入口与管理平台 `platform-api` 分别以月度 99.9% 可用性为第一版目标；
- 可用性分母只包含到达服务边界的合格请求；预期 4xx、客户端取消和明确配额拒绝不计服务错误，5xx、服务端超时、错误部署及团队负责依赖故障计入；
- platform-api 简单平台 Query/Command 的初始服务端 p95 目标为 500 ms/1 s；跨处理系统的组合读取 p95 目标为 1.5 s，并允许按契约返回 `partial`/`stale`，不得用无限等待追求完整；
- SLO 按环境和入口独立计算，预发布不计入生产 SLO；所有指标需提供分母、窗口和缺失说明。

### 9.2 可靠接收与处理及时性

- 数据接入只有在必要校验与可靠缓冲成功后才返回接收成功；在已确认接收边界内不允许已知静默丢失；
- 接收成功不是问题已生成。正常容量、有效事件且未触发明确采样/保护策略时，第一版目标为 95% 在 60 秒内可查询、99% 在 5 分钟内可查询；
- 队列/缓冲最老年龄、处理成功率、重复抑制、死信、聚合水位和查询水位分别监控；
- 真实吞吐和事件大小模型尚不存在，以上是发布目标而非已验证容量。只有负载/积压/恢复测试完成后才能对外承诺。

### 9.3 容量与保护

- 每个生产部署前记录预期账号/组织/项目、事件速率/大小、API 并发、后台任务、数据库增长、Redis 内存和对象增长假设；
- ECS 基于服务延迟、并发、CPU/内存和队列年龄扩缩容，数据库/Redis 按容量和故障边界调整；禁止只以 CPU 作为处理积压的唯一信号；
- 达到资源水位时按 PRD/D2 权威策略采样、限频或降级，并把状态、原因、水位、采样和完整性返回管理平台；
- 保护状态不得自动更改客户 allowlist、密钥、环境或业务规则，也不得把未知/部分结果显示为 0。

### 9.4 错误预算

99.9% 月度目标对应约 43.8 分钟不可用预算。预算消耗达到 50% 时限制高风险非必要发布并要求恢复计划；耗尽时暂停非关键发布，只允许修复、恢复和经风险批准的安全变更。具体多窗口 burn-rate 告警在可观测性实施规格中锁定。

## 10. 数据库迁移、应用部署与回滚

### 10.1 通用发布序列

1. 合并前完成契约、Migration、制品和影响审查；
2. 同一提交生成 SPA、API、Worker、SDK（如适用）和发布清单；
3. 部署预发布并运行核心 E2E、Migration、回滚/恢复烟雾和安全检查；
4. 生产审批者检查差异、SLO/告警、备份、兼容窗口和回滚条件；审批者不得批准自己未被独立复核的高风险变更；
5. 生产先执行兼容的 expand Migration，再部署兼容 API/Worker，观察健康和业务不变量；
6. 切换新行为、完成有界 backfill；只有旧版本和旧数据路径退出后，后续独立发布才允许 contract；
7. 部署后验证公开 API、关键业务链、队列/Outbox、数据水位、审计和告警，再关闭发布窗口。

### 10.2 数据库 Migration

- 版本化 SQL Migration 是唯一结构变更来源，由一次性 ECS Task 在受控角色下执行；应用启动不得自动改表；
- Migration 使用全局互斥/版本前置，重复运行安全失败或幂等；
- 大表 backfill 分批、可暂停、可续跑、有限并发，并监控锁、延迟和复制/存储水位；
- 部署回滚优先回滚应用并保持兼容结构，不自动运行破坏性 down Migration；数据修复需要独立审核脚本、备份点和验证；
- Migration 失败立即停止后续部署，保留错误证据并按 Runbook 恢复。

### 10.3 ECS 与 SPA

- API 和 Worker 使用独立 ECS Service/Task Definition；滚动部署必须设置健康阈值、最小健康比例、熔断和 CloudWatch 告警；
- API/Worker 在重叠版本窗口内兼容相同数据库、Outbox、任务负载和公开契约；Worker 不能先消费尚未兼容的任务格式；
- 停止任务先拒绝新流量、完成有界 drain，再退出；未完成任务由租约/幂等恢复；
- SPA 先上传内容哈希资源，再原子切换入口；旧浏览器中的旧 SPA 必须在兼容窗口内仍能调用当前 API；
- 回滚以旧 digest/旧入口为准，不重新构建。若 Migration 已进入不可逆阶段，按预先批准的 forward-fix/兼容方案执行。

### 10.4 SDK 发布

- SDK 发布与平台部署解耦，使用受保护 npm Environment、Trusted Publishing、2FA/最小权限和来源证明；
- 发布前在干净临时项目验证包安装、exports、类型、tree-shaking、示例、包内容和体积；
- 已发布版本不可视为可原地替换制品；坏版本标记 deprecated、发布补丁并提供升级说明；
- 协议不兼容、默认采集、隐私、浏览器支持或公共 API 变化必须遵守 SemVer、迁移和 ADR/协议门禁；
- 精确统一/独立包版本策略仍属于 Monorepo 与发布工程缺口，不能在 npm 流水线中临时决定。

## 11. 备份、恢复与灾难恢复

### 11.1 PostgreSQL

- 生产 RDS PostgreSQL 启用 Multi-AZ、加密、自动备份和 PITR；初始备份保留 35 天；
- 每日复制加密恢复点到独立备份账户/第二区域，权限与生产运行角色隔离；
- 单区域多可用区运行故障目标为 `RPO ≤ 5 分钟`、`RTO ≤ 60 分钟`；该目标包括实例/可用区故障、误操作在 PITR 窗口内恢复，不等于整区域自动恢复；
- 第一版区域级灾难目标为 `RPO ≤ 24 小时`、`RTO ≤ 8 小时`，依靠跨区域备份和 IaC 重建；若产品要求区域级 5 分钟/60 分钟，必须增加跨区域复制和新成本/ADR 评审；
- 每月执行数据库恢复演练，每季度执行跨系统灾难恢复演练；恢复成功必须通过业务不变量、迁移版本、审计和关键 Query/Command 验证。

### 11.2 Redis、BullMQ 与缓存

- Session Redis 采用生产高可用、加密、认证、禁止淘汰和满足安全目标的持久化/备份；故障时受保护请求失败关闭；
- Session 数据丢失可以导致重新登录，但不得恢复已撤销会话或绕过认证；恢复目标与 PostgreSQL 数据恢复目标分开记录；
- BullMQ Redis 故障后由 PostgreSQL Outbox 和权威失败记录重投；任务处理器必须幂等。普通缓存可清空重建，不进入数据 RPO；
- Session、BullMQ 和缓存不得因便利共享淘汰策略、凭据或故障域。精确 ElastiCache 拓扑、备份窗口和容量由实施基准锁定。

### 11.3 S3 对象

- 私密对象 Bucket 启用加密、版本控制、阻止公共访问和最小 Bucket Policy；
- Source Map 数据库元数据与对象摘要必须可核对；孤儿对象、缺失对象、删除失败和版本堆积有周期检查；
- 项目永久删除同时遵守 PRD 保留/删除规则，备份副本只在受控保留期内存在且不可作为普通读取路径；
- 每季度抽样恢复 Source Map/发布对象，并验证严格项目/发布/路径匹配、摘要和授权；
- 精确对象保留、非当前版本生命周期和跨区域复制等待安全/合规与区域选择，不得使用无期限默认。

## 12. 可观测性、告警与事故处理

### 12.1 信号

| 层级 | 必需信号 |
|---|---|
| Edge/API | 请求量、状态/稳定错误码、延迟、限频、WAF、目标健康、Session 依赖、下游耗时 |
| PostgreSQL | 连接、事务冲突、死锁、慢查询、存储、复制/备份、Migration、Outbox 数量与最老年龄 |
| Redis/BullMQ | Session 可用性/淘汰/复制、队列等待/延迟/活跃/失败、最老任务、重试和各任务类型资源占用 |
| 处理链路 | 接收确认、缓冲持久性、消费延迟、重复抑制、死信、问题/指标水位、告警评估暂停 |
| S3 | 上传/确认/下载/删除、摘要不一致、孤儿对象、权限拒绝；不记录签名 URL |
| 产品不变量 | 无所有者组织、重复项目/通知/任务、删除或策略传播停滞、审计写入失败、一次性秘密异常重显 |
| 前端 | 发布版本、路由错误、资源加载、核心 Web 指标和安全去敏错误；不得采集 PRD 禁止数据 |

应用采用结构化日志和跨系统关联标识；请求标识、业务 Operation、幂等键摘要和 trace 用途分离。日志、指标标签和 trace 不保存密码、Cookie、Token、完整邮箱、原始请求/响应体、Source Map、完整 URL 查询或高基数用户上下文。

### 12.2 告警与 Runbook

- P0/P1 告警必须对应用户影响或数据风险，包含 Owner、仪表盘、首要诊断和 Runbook，不对每个低价值指标直接分页；
- 关键告警覆盖公开入口 SLO、Session Redis、可靠缓冲不可写、处理积压/死信、数据库故障/备份、删除停滞、审计失败和生产部署熔断；
- 告警分为立即响应、工作时处理和趋势复查；相同根因去重，禁止告警风暴掩盖主故障；
- 事故流程包括确认影响、冻结发布、保护数据、回滚/恢复、用户沟通、证据保留、复盘和规则/测试/Runbook 回填；
- 正式值班渠道、状态页和通知对象是运营组织缺口，未确定前不能宣称 24×7 响应。

## 13. 安全、隐私与发布保护

- 生产访问使用身份联合、最小角色、短期凭据、MFA 和审计；不建立共享管理员账号；
- 生产数据库、Redis 和对象访问不授予常规开发流程；故障访问采用时间限制和审计；
- CI 执行依赖、许可证、秘密、SAST、容器和 IaC 扫描；高危/严重问题无有效豁免时阻止发布；
- Session、CSRF、Cookie、密码参数、内部能力令牌、KMS 和工作负载身份须经过安全评审和必要 ADR；
- 测试/可观测性/备份遵守 PRD 数据最小化、保留和删除；不得因调试建立第二套永久事件存储；
- Source Map 不放入公共 SPA Source Map，生产前端 Source Map 若生成，仅上传到私密受控系统，并在公开 CDN 发布前验证未泄露；
- 依赖和基础镜像建立定期升级与紧急安全补丁流程；升级仍经过兼容和回滚证据。

## 14. 发布职责与检查门禁

| 角色/Owner | 责任 |
|---|---|
| 变更作者 | 提供范围、风险、测试、文档、Migration、兼容和回滚说明 |
| 领域评审者 | 核对业务不变量、公共契约、数据和模块边界 |
| 安全评审者 | 评审认证、秘密、隐私、权限、网络和高风险供应链变化 |
| 发布负责人 | 核对候选制品、环境证据、SLO/告警、备份、审批和发布记录 |
| 生产批准者 | 独立确认生产风险和停止/回滚条件；不以作者自批替代 |
| 事故负责人 | 在故障时统一决策、时间线、沟通和恢复验证 |

发布前至少满足：

- 变更范围、文档影响、ADR/契约/迁移状态准确；
- 所有必需检查通过，豁免未过期且不覆盖禁止豁免风险；
- 同一不可变制品已在预发布验证；
- 浏览器/框架/协议兼容矩阵、SDK 体积和性能预算满足；
- 生产备份/PITR 正常，相关恢复演练在有效期内；
- Migration、部署顺序、停止条件、回滚/forward-fix 和责任人明确；
- 仪表盘、告警、Runbook、发布记录和用户可感知变更说明完整；
- 安全/隐私、Source Map、秘密、日志和测试数据检查通过。

任何机器 OpenAPI、事件协议、模块 README、IaC、CI 或可执行实现仍不存在时，只能说明设计门禁，不能勾选为已完成发布证据。

## 15. 后端能力缺口与实施/发布阻塞

| 编号 | 缺口 | 影响 | 解除条件 |
|---|---|---|---|
| TDR-GAP-01 | 目标用户地域、数据驻留和主 AWS 区域未决定 | 账号、备份、延迟、合规和灾难恢复不能最终落位 | 产品/安全/合规批准地域与数据边界，部署 ADR 记录区域选择 |
| TDR-GAP-02 | 包管理器、工作区/任务编排、版本/Changelog、受影响构建与缓存工具未决定 | 无法写真实 CI 命令、SDK 发布和制品图 | Monorepo/工程工具专题补全并接受相应 ADR |
| TDR-GAP-03 | 数据接入、可靠缓冲、处理/聚合/存储没有物理技术和完整实施规格 | 不能完成全系统 AWS 拓扑、容量、负载、备份或事件恢复 | 分别形成正式技术/数据规格、公开契约与必要 ADR |
| TDR-GAP-04 | 机器 OpenAPI、事件协议、数据模型、Migration 和模块 README 不存在 | 契约、集成、E2E 与发布矩阵没有可执行来源 | 按文档规范建立唯一权威来源和生成/兼容门禁 |
| TDR-GAP-05 | Node/PostgreSQL/Redis、AWS 服务配置、实例、配额、连接池、任务并发/重试等精确版本与容量未基准化 | 无法创建安全生产配置或证明 SLO | 在目标区域完成容量/故障/成本基准并在实施规格锁定 |
| TDR-GAP-06 | 真实 Safari/iOS/Android 设备和框架版本测试提供方未决定 | 浏览器/框架承诺缺少发布证据 | 建立设备实验室或可信设备云，并形成兼容矩阵文档 |
| TDR-GAP-07 | SDK/SPA 性能参考工程、设备档位和测量基线不存在 | 量化预算尚未被真实实现验证 | 建立可复现基准，首次发布前验证或通过正式评审调整 |
| TDR-GAP-08 | Session/CSRF/Cookie、密码参数、签名/KMS、邮件供应商与安全期限未评审 | 认证、邀请、内部授权和邮件链路不能上线 | 完成安全设计、供应商评审和必要 ADR/产品规则 |
| TDR-GAP-09 | A5 账号删除、D2 平台管理员、通知/Operation/死信等保留期仍有产品规则缺口 | 相应页面和数据生命周期不能发布 | 追加并批准产品/安全规则，补全公开契约和删除测试 |
| TDR-GAP-10 | 正式发布组织、生产批准者、值班渠道、状态页、事故沟通和成本预算未确定 | 无法证明持续运营与响应责任 | 指定角色/渠道/预算并批准 Runbook；不要求新增第一版产品功能 |

缺口不阻止用户批准设计，但会分别阻止 ADR、writing-plans、实现或发布。不得使用默认云参数、框架约定或假接口绕过。

## 17. 已否决、延后与重新评估

| 方案 | 当前处理 | 重新评估条件 |
|---|---|---|
| Kubernetes/EKS | 第一版否决；少量部署单元不需要控制面复杂度 | ECS/Fargate 无法满足经测量隔离、调度或扩展需求 |
| 多云、跨区域双活 | 第一版否决 | 明确的合规、地域、可用性或商业连续性要求 |
| 直接从分支在生产重建 | 否决；破坏同一制品晋级和可追溯性 | 不重新评估，除非有等价可验证的供应链方案 |
| 自动破坏性 down Migration | 否决 | 不重新评估；数据恢复使用备份/forward-fix/独立修复 |
| SDK `unpublish` 作为回滚 | 否决 | 不重新评估；使用 deprecate、补丁和迁移说明 |
| 每个 PR 完整 AWS 全栈环境 | 第一版默认不采用 | 高风险并行集成需求证明共享预发布不足，且成本/清理可治理 |
| 只运行 Chromium 或只用 WebKit 代替 Safari | 否决 | 不重新评估；公共兼容承诺需要对应真实引擎/设备证据 |
| 第一版 Storybook/完整视觉平台 | 沿用前端技术栈否决 | Aurora UI 成为跨应用产品或出现独立设计评审需求 |
| 区域级 5 分钟 RPO/60 分钟 RTO | 当前延后，不伪装已满足 | 产品/合规要求提高并接受跨区域复制、成本和演练复杂度 |
